# 智选购 MVP 产品需求文档（PRD）

## 1. 文档定位

- 项目：智选购（AI 购）
- 版本：MVP v0.1
- 状态：待开发
- 设计依据：[智选购 AI 导购 MVP 设计文档](智选购-ai导购-mvp-design.md)
- 读者：产品、前端、Go 后端、测试人员与面试复盘者

本文定义用户价值、功能范围和可验收的产品行为。服务拆分、数据模型与一致性机制以 [architecture.md](architecture.md) 为准；页面状态与交互细节以 [interaction.md](interaction.md) 为准。

## 2. 产品定位

智选购是面向消费决策场景的 AI 电商导购平台。用户以自然语言表达预算、用途和偏好，系统将需求转为受控的商品检索与业务查询，返回带有真实价格、库存、优惠快照和推荐理由的商品结果；用户可继续完成购物车、订单和余额支付。

产品的核心不是让模型替代交易系统，而是让模型负责理解与排序，后端业务服务负责价格、库存、优惠和交易的最终判断。

## 3. 目标与成功标准

### 3.1 产品目标

1. 让用户从模糊购买需求进入可执行的商品选择与下单链路。
2. 让每条推荐都能解释“为什么推荐”和“业务数据从哪里来”。
3. 让运营人员能管理商品资料，并排查一次 Agent 导购执行中的模型、Tool 或服务故障。
4. 用一个可本地运行的 MVP 展示 Go 微服务、RAG、Agent、消息可靠性和交易一致性能力。

### 3.2 可验收成功标准

| 目标 | 可观察结果 |
| --- | --- |
| AI 导购闭环 | 用户可输入购买需求，得到至少 3 个通过后端校验的推荐 SKU，并进入商品详情或购物车。 |
| 推荐可信 | 推荐卡片同时显示理由、价格、库存状态与优惠快照；模型文本不能直接成为交易字段。 |
| 交易正确 | 相同 `request_id` 的重复建单返回同一订单；重复余额支付不重复扣款；库存不足时支付失败且不产生资金流水。 |
| RAG 可运营 | 资料上传接口不等待向量化；运营人员可查看文档版本、处理状态、失败原因并重试。 |
| Agent 可排障 | 一次 Run 的每个模型或 Tool Step 均可查看状态、耗时、脱敏输入输出和关联 `trace_id`。 |

本阶段不承诺未经固定环境与可重复压测验证的性能数字。

## 4. 用户与权限

| 角色 | 主要目标 | 可操作范围 |
| --- | --- | --- |
| 普通用户 | 找商品、确认商品信息、购买和评价 | 自己的会话、画像、地址、购物车、订单、评价与推荐记录 |
| 运营人员 | 维护商品资料、查看处理状态与导购质量 | 商品资料、知识库任务、Agent Run 回放、只读运营统计 |
| 系统任务 | 异步完成资料处理、事件投递、统计和缓存补偿 | 仅处理已持久化任务；不直接替用户发起交易 |

所有用户资源按 JWT 中的当前用户身份进行归属校验。运营入口需单独角色授权；仅持有资源 ID 不构成访问权限。

## 5. MVP 范围

### 5.1 必须交付

1. 商品浏览：商品列表、分类/关键字筛选、SKU 详情、规格、价格、库存状态和优惠展示。
2. AI 导购：多轮会话、受控 Tool Calling、推荐结果、后端二次校验、推荐快照和 SSE 进度反馈。
3. 商品问答：围绕单一商品的问题，优先使用当前 READY 文档版本检索；知识库不可用时降级为结构化字段或规则问答。
4. 交易闭环：购物车、地址选择、创建待支付订单、余额支付、订单状态查看和评价提交。
5. 运营最小能力：商品资料上传、版本和处理状态查看、失败重试、Agent Run/Step 时间线回放。
6. 可靠异步：知识库处理、行为和评价事件使用 Kafka；事件投递与消费均可幂等、重试和进入 dead-letter。

### 5.2 明确不做

- 多 Agent 协作、模型计费、Prompt 在线运营平台和多租户。
- 秒杀、Redis 库存预扣、复杂优惠叠加、退款和真实第三方支付。
- 完整商品/营销后台、推荐模型训练和全量经营 BI。
- 让 LLM 直接执行 SQL、读写 Redis、扣库存、扣余额、创建订单或写入优惠。

## 6. 核心用户故事

### 6.1 导购与推荐

**作为普通用户**，我希望输入“预算 5000 元，适合编程和轻度游戏的笔记本”，以便获得可购买的候选商品。

- 系统保存用户消息并创建 `AgentRun`，前端实时看到处理中、Tool 调用或失败状态。
- Agent 只可调用商品检索、用户画像、价格库存和优惠查询等受控只读 Tool。
- 最终至少返回 3 个有效 SKU；若候选不足，应明确说明缺少的条件或可放宽的条件。
- 推荐理由由模型生成；价格、库存、优惠和可售状态只能由后端 Tool 返回并保存为快照。
- 商品不再可售、价格校验失败或 SKU 不存在时，结果不得出现在最终推荐中。

### 6.2 商品问答

**作为普通用户**，我希望在商品详情页询问规格和售后信息，以便在下单前确认风险。

- 系统按 `product_id`、资料类型、当前 READY 版本过滤检索内容。
- 回答展示资料来源，包括文档类型、版本和章节/页码；找不到依据时明确说明而不是编造。
- 价格、库存、优惠、订单等确定性问题不由 RAG 猜测，转入相应业务查询或规则回答。

### 6.3 下单与余额支付

**作为普通用户**，我希望将推荐商品购买下来，并在网络重试时不被重复扣款。

- 用户确认地址和购物车后，创建状态为 `PENDING_PAYMENT` 的订单，订单明细写入商品、规格、价格和地址快照。
- 创建订单请求必须携带 `request_id`；重复请求返回首次成功创建的订单。
- 余额支付时才扣减库存。余额、库存、订单状态、钱包流水和 Outbox 事件在同一 MySQL transaction 内完成。
- 余额不足、库存不足或订单状态非法时，不产生部分扣款和部分成功状态。

### 6.4 资料运营与排障

**作为运营人员**，我希望上传商品资料后继续处理其他工作，并能定位失败原因。

- 上传成功后立即返回文档记录与 `PENDING` 状态；解析、切分、Embedding、向量写入异步执行。
- 新版本只有处理至 `READY` 后才参与检索；旧版本保留审计记录但不可被正常召回。
- 运营人员可查看单次导购 Run 的 Step 顺序、状态、耗时、脱敏输入输出和错误分类，并能按 `trace_id` 关联服务日志。

## 7. 功能需求

| 编号 | 功能 | 必要行为 |
| --- | --- | --- |
| FR-01 | 商品目录 | 返回已上架 SPU 与可售 SKU；价格、规格和库存在详情页按 SKU 呈现。 |
| FR-02 | AI 会话 | 新消息创建一个 Run；单 Run 最多 8 个 Step、总时长最多 30 秒。 |
| FR-03 | 推荐校验 | Agent 输出只能包含 SKU ID、排序和理由；后端重新获取价格、库存、优惠并过滤无效 SKU。 |
| FR-04 | 商品问答 | 答案附来源；无可靠来源时给出受控降级回复。 |
| FR-05 | 购物车与订单 | 购物车按用户隔离；创建订单使用幂等键并生成不可变快照。 |
| FR-06 | 余额支付 | 使用余额支付已创建订单；成功后显示 `PAID`，重复请求返回既有成功结果。 |
| FR-07 | 评价与行为 | 评价仅限已购买订单项；评价和行为事件异步投递，重复消费不重复统计。 |
| FR-08 | 知识库 | 支持 DETAIL、SPEC、FAQ、AFTER_SALE 四类资料，提供状态、版本、错误和重试信息。 |
| FR-09 | Agent 可观测性 | 管理端可以检索 Run 并查看 AgentStep 时间线，敏感字段必须脱敏。 |

## 8. 非功能需求与产品约束

- **正确性**：MySQL 是价格、库存、余额、订单和推荐快照的最终事实源；金额使用 `DECIMAL(12,2)`。
- **可解释性**：每个最终推荐都能关联 `run_id`、SKU、校验结果和快照；每次 Agent 执行均可回放。
- **可用性**：模型、Tool 或知识库失败时，用户看到稳定、简短、可行动的错误文案，不能暴露原始依赖报文或敏感信息。
- **安全性**：模型 API Key、JWT、密码和存储凭证不得写入代码、日志或示例文档；Agent 输入输出、地址和手机号记录前脱敏。
- **数据保留**：Agent 消息和 Step 原始内容仅保存脱敏结果，默认保存 90 天；订单、钱包流水和推荐快照不物理删除。
- **性能结论**：任何 P95、QPS、缓存命中率等数值必须附带环境、数据规模、并发、预热策略和测试命令；未实测不填写数值。

## 9. 发布验收

MVP 可进入演示阶段需要同时满足：

1. 从自然语言推荐到余额支付的主链路可在本地 Docker Compose 环境完成。
2. 模型返回无效 SKU、Tool 超时、库存不足、余额不足、重复建单和重复支付均有可验证处理结果。
3. 文档重复投递、资料版本切换、Embedding 失败重试、Kafka 重复消费和 dead-letter 路径可被测试覆盖。
4. 运营人员可查看文档处理状态和至少一条完整的 Agent Run 时间线。
5. 所有演示数据、日志和截图不包含真实凭证、地址、手机号或支付信息。
