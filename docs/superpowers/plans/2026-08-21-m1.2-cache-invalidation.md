# M1.2 Cache Invalidation Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (- [ ]) syntax for tracking.

**Goal:** Persist post-write catalog cache invalidations transactionally, delete affected Redis product-detail keys immediately after commit, and retry delayed deletes through a bounded product-service worker.

**Architecture:** A catalog-owned mutation repository updates products and writes concrete cache_invalidation_tasks rows in one MySQL transaction. CatalogMutationService deletes returned keys only after commit. CacheInvalidationWorker leases due rows, calls DetailCache, and transitions rows through PENDING, RUNNING, DONE, or DEAD with bounded retry backoff. No public product write endpoint is introduced.

**Tech Stack:** Go 1.25, database/sql, MySQL 8.4, go-sqlmock, Redis/go-redis, Go-zero zRPC configuration, Docker Compose.

CREATE TABLE cache_invalidation_tasks (
    id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    cache_key VARCHAR(256) NOT NULL,
    execute_at DATETIME(3) NOT NULL,
    retry_count INT UNSIGNED NOT NULL DEFAULT 0,

### Task 3: Lease-based delayed deletion worker

**Files:**
- Create: services/product-service/internal/catalog/cache_invalidation.go
- Create: services/product-service/internal/catalog/cache_invalidation_test.go

- [ ] **Step 1: Write failing worker state-machine tests**

Use a fake task store and fake cache for these cases: future task is not claimed; due task becomes DONE; first failure becomes PENDING with retry count 1 and RetryBaseDelay; next failure doubles but caps at RetryMaxDelay; failure at MaxRetries becomes DEAD; stale RUNNING is reclaimed; live RUNNING is not reclaimed; Run exits on context cancellation.

~~~go
worker, err := NewCacheInvalidationWorker(store, cache, CacheInvalidationConfig{
    PollInterval: time.Millisecond, BatchSize: 2, LeaseDuration: time.Second,
    MaxRetries: 2, RetryBaseDelay: time.Second, RetryMaxDelay: 4 * time.Second,
    CallTimeout: time.Second,
})
err = worker.RunOnce(context.Background(), now)
~~~

- [ ] **Step 2: Run test to verify RED**

Run: go test ./services/product-service/internal/catalog -run TestCacheInvalidationWorker -count=1

Expected: FAIL because worker, statuses, and config do not exist.

- [ ] **Step 3: Implement claim, transitions, and retry**

Define CacheInvalidationTask, status constants, CacheInvalidationTaskStore, and CacheInvalidationConfig. The MySQL store claims at most BatchSize PENDING rows with execute_at <= now and stale RUNNING rows with locked_at <= now - LeaseDuration in a short transaction using SELECT ... FOR UPDATE SKIP LOCKED. It marks selected rows RUNNING with one locked_at value before Commit.

Implement NewCacheInvalidationWorker, Run, and RunOnce. Run uses time.NewTicker and stops on ctx.Done. RunOnce deletes each claimed key with context.WithTimeout, marks success DONE, and records only "cache delete failed" on failure. Failure increments retry_count and sets PENDING with min(RetryBaseDelay * 2^(retryCount-1), RetryMaxDelay); the limit transition is DEAD. Mark transitions match task ID and lease timestamp so a stale worker cannot overwrite a later lease.

## Plan Self-Review

- This plan covers schema, atomic task persistence, post-commit deletion, concrete SKU keys, delayed worker, bounded retry, stale lease recovery, Redis degradation, unit tests, real Docker validation, and documentation.
- It introduces no public catalog mutation API, Redis wildcard deletion, Kafka cache flow, or inventory cache dependency.
- The schema update is applied deterministically in a fresh isolated Docker volume during real validation.
