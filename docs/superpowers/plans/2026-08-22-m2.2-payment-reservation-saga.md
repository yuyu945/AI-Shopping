# M2.2 Payment Reservation Saga Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Implement idempotent wallet payment with product-owned atomic reservations, reliable confirmation, and crash-safe recovery.

**Architecture:** M2.1 must first supply a MySQL-backed order repository and authenticated order RPC. M2.2 uses short local transactions only: claim in `trade_db`, reserve in `catalog_db`, then settle in `trade_db`. A paid settlement records an Outbox confirmation; reconciliation workers, rather than request memory, resolve interrupted attempts and expired reservations.

**Tech Stack:** Go 1.25, Go-zero zRPC, MySQL 8.4, Kafka, `go-sqlmock`, table-driven unit tests, Docker integration tests.

---

## Preconditions

- M2.1 has completed the real order repository, order RPC, and Gateway route. Do not implement payment against the current in-memory repository.
- Migrations are upgrade-safe for an existing database; do not rely solely on Docker's first-start init directory.

- [ ] **Step 3: Implement claim, reserve, and settle**

```go
type ReservationClient interface {
	ReserveStock(context.Context, ReserveRequest) (Reservation, error)
	ReleaseReservation(context.Context, string) error
	GetReservation(context.Context, string) (Reservation, error)
}
```

`ClaimPayment` conditionally changes only `PENDING_PAYMENT` to `PAYMENT_PROCESSING` and persists generated attempt/reservation IDs. After product reservation succeeds, `SettleWalletPayment` locks the matching order in one `trade_db` transaction. When `total_amount > 0`, it locks, checks, and updates the wallet and writes the unique debit ledger. When `total_amount == 0`, it does not query or update the wallet and writes no ledger entry. Both paths update the order to `PAID` and insert the confirmation Outbox in that same transaction; an Outbox insert failure rolls back the order, wallet update, and ledger entry as applicable. It never calls product-service while the transaction is open. The product consumer confirms the reservation and writes its consumption record in one `catalog_db` transaction, so a failed confirmation remains retryable. Insufficient balance resets the matching claim and requests a best-effort release.

- [ ] **Step 3: Implement safe reconciliation**

Order recovery leases stale `PAYMENT_PROCESSING` attempts, reads the persisted reservation, then resumes settlement or resets/releases only for explicit non-paid outcomes. Product expiry leases expired `RESERVED` rows, confirms `PAID`, releases `PENDING_PAYMENT` or `CLOSED`, and postpones processing or timeout results with bounded backoff. Every lease and state update uses compare-and-set conditions.
