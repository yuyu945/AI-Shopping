# M1.2 Cache Invalidation and Retry Design

## Goal

Complete the remaining M1.2 cache consistency path for catalog detail changes. A product detail mutation must atomically persist its MySQL fact and a delayed Redis invalidation task, remove the affected cache entries immediately after commit, and retry the delayed deletion outside request handling. The implementation does not add a public catalog-management API and does not use Redis as an inventory fact source.

## Scope and Boundary

`product-service` remains the sole owner of the `catalog_db` task table and its worker. The initial mutation surface is an internal `CatalogMutationService.UpdateProductDetail` method for future catalog write flows; it is not registered in the product protobuf or Gateway routes. The current product list/detail read APIs retain their behavior.

The design applies to the versioned keys returned by `ProductCacheKey`:

```text
product:v1:detail:{product_id}:sku:all
product:v1:detail:{product_id}:sku:{sku_id}
```

Every product detail mutation invalidates the `all` key and a concrete key for every SKU currently associated with the product. It never uses a Redis wildcard/scan delete. This also removes a previously cached SKU that becomes inactive during a later catalog write.

## Data Model

`catalog_db.cache_invalidation_tasks` is a service-owned InnoDB table with these fields:

```text
id                 BIGINT UNSIGNED PK AUTO_INCREMENT
cache_key          VARCHAR(256) NOT NULL
execute_at         DATETIME(3) NOT NULL
retry_count        INT UNSIGNED NOT NULL DEFAULT 0
status             VARCHAR(16) NOT NULL
last_error         VARCHAR(512) NULL
locked_at          DATETIME(3) NULL
created_at         DATETIME(3) NOT NULL
updated_at         DATETIME(3) NOT NULL
executed_at        DATETIME(3) NULL
INDEX(status, execute_at, id)
INDEX(status, locked_at, id)
INDEX(cache_key, execute_at)
```

The state transitions are:

```text
PENDING -> RUNNING -> DONE
                 -> PENDING  (retryable delete failure)
                 -> DEAD     (retry limit reached)
RUNNING -> PENDING           (lease expired after worker interruption)
```

Tasks may have identical keys and execution times; they represent independent post-write invalidations and are intentionally not deduplicated. `execute_at` is the next eligible processing time. `retry_count` counts failed worker deletion attempts only, not the immediate post-commit deletion attempt.

## Write Flow

`CatalogMutationService.UpdateProductDetail(ctx, productID, detailMarkdown)` validates the product ID and executes one local MySQL transaction:

1. Read all SKU IDs for the product, including inactive SKUs.
2. Update `products.detail_markdown` and increment `products.version`; zero affected rows is a typed not-found result.
3. Insert one `PENDING` task per concrete affected cache key with `execute_at = now + delayedDeleteDelay`.
4. Commit the transaction.

Only after a successful commit, the service attempts `DetailCache.Delete` for every affected key using a bounded context. A failure is deliberately not returned as a failed catalog write: the already-persisted task is the recovery record. A transaction error skips all immediate cache deletions. When Redis is unavailable, the service still commits the catalog mutation and tasks.

## Worker Flow

The worker has a `Run(ctx)` loop and a separately testable `RunOnce(ctx, now)` method. It is started by `product-service` only when the Redis detail cache was successfully initialized. Its ticker and all database/cache calls inherit cancellation or explicit timeouts; it never sleeps in an HTTP/gRPC request path.

`RunOnce` operates in bounded batches:

1. In a short transaction, select due `PENDING` tasks and stale `RUNNING` tasks using row locks, then mark the selected rows `RUNNING` and set `locked_at`.
2. Outside that transaction, call `DetailCache.Delete` once for each claimed cache key.
3. On success, set `DONE`, clear the lease, and set `executed_at`.
4. On failure below the retry limit, increment `retry_count`, set `PENDING`, clear the lease, persist a safe dependency summary in `last_error`, and move `execute_at` by bounded exponential backoff.
5. On failure at the retry limit, set `DEAD`, clear the lease, and retain the safe failure summary for diagnostics.

The worker claims stale leases after `leaseDuration`; this makes an interrupted process recoverable without concurrent workers repeatedly deleting the same task. SQL errors and Redis errors remain internal diagnostics and are never exposed through public HTTP responses.

## Configuration

`product-service` owns these runtime settings in its YAML configuration with conservative defaults:

```text
CacheInvalidation.PollInterval: 1s
CacheInvalidation.BatchSize: 50
CacheInvalidation.DelayedDeleteDelay: 1s
CacheInvalidation.LeaseDuration: 30s
CacheInvalidation.MaxRetries: 5
CacheInvalidation.RetryBaseDelay: 1s
CacheInvalidation.RetryMaxDelay: 30s
```

`BatchSize`, delays, retry count, and lease duration are validated at startup. Cache initialization failure continues to degrade product reads to MySQL and leaves the worker stopped; no task is discarded.

## Testing and Validation

Table-driven unit and sqlmock tests must prove:

1. The mutation transaction updates the product, writes all concrete cache tasks, commits, then immediately deletes each key.
2. A transaction rollback creates no durable task and performs no immediate cache deletion.
3. A due task is deleted once and marked `DONE`; a future task is not claimed.
4. A deletion failure is rescheduled with increasing bounded delay; the last permitted failure becomes `DEAD`.
5. A stale `RUNNING` task is reclaimable, while a live lease is not.
6. Inventory reads continue to query MySQL and do not gain a Redis dependency.

Real Docker validation will update a seed product through the internal mutation service, confirm the seeded `all` and SKU keys disappear immediately, observe the delayed task reach `DONE`, then simulate a Redis deletion failure to confirm persistence and retry behavior. It must not claim that cached inventory is authoritative.

The build-tagged integration test is write-enabled only when `AI_SHOPPING_INTEGRATION=1`, `AI_SHOPPING_INTEGRATION_ISOLATED=m12cacheverify`, and a nonzero `AI_SHOPPING_REDIS_DB` are set. Before loading any fixture or issuing a mutation, it verifies that the connected database is `catalog_db`, `cache_invalidation_tasks` has zero rows, and Redis `DBSIZE` is zero in the selected Redis DB. A missing/mismatched isolation sentinel skips the test; invalid explicit configuration or nonempty isolated stores fails before a write. Cleanup is limited to the selected fixture product, its concrete cache keys, and invalidation tasks created for those keys.

## Deliberate Omissions

This change does not create catalog-admin UI/API, use Redis pattern scans, retry from request goroutines, add Kafka cache invalidation, or delete/alter inventory based on cached data. `DEAD` task replay tooling is deferred until there is an operator surface; the row is retained for inspection and a future controlled replay operation.
