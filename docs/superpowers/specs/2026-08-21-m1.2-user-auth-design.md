# M1.2 User Authentication and Ownership Design

## Goal

Complete the remaining user portion of M1.2 with a real registration-to-authenticated-address path. A browser client can register or log in, receive a short-lived JWT, read and update only its own profile, and manage only its own delivery addresses. The implementation keeps `user-service` as the sole owner of `user_db` and does not add refresh tokens, roles, token revocation, wallet initialization, or cross-service database access.

## Implemented State

`user_db` owns `users`, `user_profiles`, and `user_addresses`. `user-service` implements registration, login, JWT issuance and verification, profile operations, and address ownership enforcement. The Gateway validates JWTs for protected user routes, forwards the authenticated bearer to user-service gRPC, and exposes the public auth endpoints. `product-service` remains the reference for generated gRPC contracts, service-owned database access, typed application DTOs, context timeouts, stable gRPC status mapping, and Gateway HTTP adapters.

## Chosen Architecture

`user-service` owns password verification and JWT issuance. It signs HS256 access tokens with the required `AI_SHOPPING_JWT_SECRET` runtime secret. The token has issuer `ai-shopping`, a decimal user ID in `sub`, the canonical email in `email`, and `iat`/`exp` claims; its fixed lifetime is 24 hours.

The Gateway validates the bearer token before every protected `/api/v1/users/me...` route. It saves the verified principal and the original bearer value in the request context. The user gRPC adapter forwards the bearer value to `user-service` as gRPC `authorization` metadata. The user gRPC server verifies that same token again and derives the current user ID only from verified claims. Protected RPC messages contain no caller-controlled `user_id` field. This second verification makes ownership enforcement independent of a client-supplied forwarding header.

`GET /api/v1/products...`, `/healthz`, `POST /api/v1/auth/register`, and `POST /api/v1/auth/login` remain public. No existing product route changes behavior.

## Data and Invariants

No schema migration is required. Registration creates the `users` row and its empty `user_profiles` row in one local `user_db` transaction. Email is trimmed and lower-cased before lookup or insert. Passwords are accepted only when their trimmed UTF-8 byte length is 8 through 72, then stored exclusively with bcrypt; passwords and hashes never appear in response bodies or logs.

The profile response uses a DTO, never a SQL model. It contains user ID, canonical email, budget values encoded as decimal strings, profile version, and a JSON preference object. Profile updates validate that both supplied budget values are decimal values with at most two fractional digits and that `budget_min <= budget_max` when both are present. An update increments `profile_version`.

All address reads and mutations include `WHERE id = ? AND user_id = ?`. A non-owned address is indistinguishable from a missing address and returns stable `NOT_FOUND`. Address data is persisted but is not logged. On address creation, the first address is made default. A request that sets `is_default=true` clears the user's existing default and sets the selected address in the same transaction. Updating an address follows the same rule. Deleting a default address promotes the lowest remaining address ID to default in the same transaction; deleting the last address leaves no default.

## API Surface

The Gateway exposes these JSON endpoints:

| Endpoint | Authentication | Request/response behavior |
| --- | --- | --- |
| `POST /api/v1/auth/register` | public | Accepts `email` and `password`; atomically creates the user/profile and returns an access token plus a safe user summary. Duplicate email returns a stable validation error without database details. |
| `POST /api/v1/auth/login` | public | Accepts `email` and `password`; returns an access token plus the same safe user summary. Invalid credentials return `UNAUTHENTICATED`. |
| `GET /api/v1/users/me` | bearer token | Returns the current user's profile. |
| `PUT /api/v1/users/me/profile` | bearer token | Replaces the supplied profile fields after decimal/range validation and returns the updated profile. |
| `GET /api/v1/users/me/addresses` | bearer token | Returns only the current user's addresses. |
| `POST /api/v1/users/me/addresses` | bearer token | Creates an address for the current user and returns it. |
| `PUT /api/v1/users/me/addresses/{id}` | bearer token | Updates only a current-user address and returns it. |
| `DELETE /api/v1/users/me/addresses/{id}` | bearer token | Deletes only a current-user address and returns HTTP 204. |

Request validation rejects unknown malformed IDs, empty address fields, receiver names longer than 128 bytes, phones longer than 32 bytes, location fields longer than 64 bytes, and details longer than 512 bytes before calling gRPC. The HTTP layer maps `INVALID_ARGUMENT` to 400, `UNAUTHENTICATED` to 401, `NOT_FOUND` to 404, `DEADLINE_EXCEEDED`/`UNAVAILABLE` to 504 with `DEPENDENCY_TIMEOUT`, and all other failures to a generic 500. It never expose SQL, bcrypt, JWT, or gRPC details.

The user proto uses explicit request/response messages for registration, login, profile, and addresses. Profile and address RPCs do not accept `user_id`; the server extracts the principal from verified gRPC metadata. Future order-service address checks will use a separate internal ownership-validation RPC carrying the requesting user ID and address ID, rather than reading `user_db` directly.

## Failure and Security Behavior

`AI_SHOPPING_JWT_SECRET` is mandatory for the Gateway and `user-service`, is added only as a blank entry to `.env.example`, and is never logged. It must contain at least 32 bytes. Invalid, expired, incorrectly issued, or malformed bearer tokens produce `UNAUTHENTICATED` before a protected handler runs. The Gateway removes any caller-provided identity forwarding headers; authorization is forwarded only from the authenticated request context.

The user repository uses only parameterized SQL. Database, bcrypt, and JWT parser failures are wrapped in internal application errors. Every repository and RPC call receives a context with an explicit timeout. Trace context remains unchanged; `X-Trace-ID` is preserved on auth and user responses using the existing Gateway pattern.

## Testing and Validation

Table-driven unit tests cover email/password validation, JWT signing and expiry/issuer rejection, duplicate registration, invalid login, canonical email lookup, profile budget boundaries, profile version increment, first/default address behavior, ownership denial, and default promotion after deletion. Repository tests assert parameterized SQL and transaction rollback paths. gRPC-server tests prove protected methods reject missing or invalid metadata and never accept a request user ID. Gateway handler and middleware tests cover public-route bypass, missing/malformed/expired bearer tokens, stable HTTP errors, trace propagation, and address/profile route mapping without error-detail leakage.

Before closing the implementation milestone, run `gofmt`, focused user/Gateway tests, `go test ./... -count=1`, `go vet ./...`, `git diff --check`, Docker Compose validation, and a real local MySQL/Gateway flow for registration, login, protected profile access, address ownership rejection, and default-address transition.

## Risks and Deliberate Omissions

HS256 requires both Gateway and `user-service` to hold the same local secret. This is acceptable for the MVP because configuration is environment-only and services are deployed together; asymmetric key rotation, refresh-token storage, revocation, and role authorization are intentionally deferred. The user schema has no role column, so this change does not claim to implement the later operator role described in the broader PRD.
