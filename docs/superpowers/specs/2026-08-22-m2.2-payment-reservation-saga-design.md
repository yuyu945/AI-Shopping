# M2.2 Payment Reservation Saga Design

## Goal

在不违反服务数据所有权的前提下完成余额支付：不重复扣款、不超卖、支付完成后不会因确认延迟释放库存，并能从进程或依赖故障中恢复。

## Decision

采用库存预留 Saga，拒绝跨 schema 共享 transaction。`product-service` 独占 `catalog_db.inventory` 与预留记录；`order-service` 独占 `trade_db` 的订单、钱包、流水和 Outbox。MySQL 在每个服务内仍是事实源，Redis 不参与支付或库存判断。

## Data And State

`orders` 新增 `payment_attempt_id`、`reservation_id`、`payment_started_at`。支付状态为：

```text
PENDING_PAYMENT -> PAYMENT_PROCESSING -> PAID
PAYMENT_PROCESSING -> PENDING_PAYMENT | CLOSED
```

`catalog_db.inventory_reservations` 保存 `reservation_id`、`order_no`、`payment_attempt_id`、`sku_id`、`quantity`、`status`、`expires_at` 与结算时间。唯一键为 `(reservation_id, sku_id)`；状态仅允许 `RESERVED -> CONFIRMED | RELEASED`。该表不创建指向 `trade_db` 的物理外键。

## Protocol

1. order-service 在短 transaction 中使用条件更新认领支付：只允许 `PENDING_PAYMENT` 创建一次 `payment_attempt_id`/`reservation_id` 并进入 `PAYMENT_PROCESSING`。
2. order-service 调用 `product-service.ReserveStock`。请求含两个 ID、订单号和全部 SKU 数量。product-service 在一个 catalog transaction 中逐项执行条件库存更新和预留插入；任一项失败 rollback 全部。相同 reservation ID 重试必须返回原预留；同 ID 不同 payload 返回 `IDEMPOTENCY_CONFLICT`。
3. order-service 在 trade transaction 中重新锁定匹配的订单和钱包，校验余额，写唯一钱包流水，更新为 `PAID`，并写 topic 为 `inventory.reservation.confirm`、key 为 `reservation_id` 的 Outbox 事件。
4. product-side consumer 以 `(event_id, consumer_group)` 幂等消费确认事件，按 reservation ID 将全部 `RESERVED` 记录置为 `CONFIRMED`。已确认重放成功返回。

`ReserveStock`、`ConfirmReservation`、`ReleaseReservation` 和订单结算状态查询均须使用限时 gRPC 和 service-to-service authentication。product-service 启动时要求 `AI_SHOPPING_INTERNAL_SERVICE_TOKEN`；四个预留 RPC（含 `GetReservation`）要求 gRPC incoming metadata `x-ai-shopping-service-token` 与该 secret 完全匹配，缺失或无效时返回 `Unauthenticated` 和稳定消息 `internal service authentication required`。服务凭证只来自环境变量或秘密管理，不写入日志和文档示例。

## Failure And Recovery

- 库存不足：product transaction rollback，order 仅将匹配尝试恢复为 `PENDING_PAYMENT`。
- 余额不足或 trade transaction rollback：order 恢复订单并 best-effort 调用 `ReleaseReservation`；调用失败由预留过期 worker 收敛。
- Outbox/确认失败：订单仍为 `PAID`，Outbox 重试确认；不得直接释放。
- 进程崩溃：order recovery worker 扫描 `PAYMENT_PROCESSING`。它按持久化 IDs 查询 product 预留；不存在则恢复订单，有预留则继续结算或在余额不足时恢复并释放。
- 预留到期：product worker 查询 order 的内部结算状态。`PAID` 确认，`PENDING_PAYMENT`/`CLOSED` 释放；`PAYMENT_PROCESSING` 交给 order recovery 后再重试。任何调用超时都保留预留并写 retry，不得猜测释放。

## External Semantics

- 已支付的重复请求返回首次支付结果。
- 相同支付仍在结算返回 `PAYMENT_IN_PROGRESS`，客户端应查询订单状态。
- 库存不足返回 `OUT_OF_STOCK`，余额不足返回 `INSUFFICIENT_BALANCE`。
- 订单状态不允许支付时返回稳定的 `IDEMPOTENCY_CONFLICT`；依赖超时返回 `DEPENDENCY_TIMEOUT`，不泄露底层错误。

## Validation

测试必须覆盖：多 SKU 原子预留、余额不足释放、重复和并发支付、wallet transaction rollback、确认事件重放、支付完成后确认延迟、预留到期时订单查询超时，以及 `PAYMENT_PROCESSING` 崩溃恢复。集成测试在隔离 MySQL/Kafka 环境中同时断言订单、余额、流水、库存、预留和 Outbox 的最终状态。
