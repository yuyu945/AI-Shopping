# M3.1 Knowledge Upload and Outbox Design

## Goal

M3.1 builds the first reliable knowledge-service slice: operators can register a product document upload, the original file is stored in MinIO, metadata is saved in `knowledge_db`, and a `knowledge.document.ingest` event is durably recorded for asynchronous publication.

The upload API returns immediately with a document number, version, and `PENDING` status. It does not parse files, generate chunks, call Embedding, or write Milvus vectors; those belong to M3.2.

## Current Behavior

`knowledge-service` is currently a startup skeleton with `services/knowledge-service/cmd/main.go` and `services/knowledge-service/etc/knowledge-service.yaml`. `deploy/mysql/init/05-knowledge-schema.sql` only creates the `knowledge_db` schema placeholder. Kafka topics already include `knowledge.document.ingest` and `knowledge.chunk.embed` in `deploy/kafka/create-topics.sh`. Runtime config already exposes `AI_SHOPPING_MINIO_ENDPOINT` and `AI_SHOPPING_KAFKA_BROKERS`, but the Go module does not yet include a MinIO SDK.

## Scope

M3.1 includes:

- `knowledge_documents` metadata with fixed doc types: `DETAIL`, `SPEC`, `FAQ`, `AFTER_SALE`.
- Knowledge-owned `outbox_events`, `event_consumptions`, and `embedding_tasks` tables.
- A repository/service layer that writes document metadata and `knowledge.document.ingest` Outbox in one `knowledge_db` transaction.
- A file storage adapter boundary and MinIO implementation.
- A knowledge upload RPC and Gateway route.
- A knowledge Outbox worker that leases pending events, publishes Kafka messages, retries with bounded backoff, and never deletes failed events.
- Unit and contract tests for schema, document validation, duplicate upload semantics, upload transaction rollback, and Outbox retry behavior.

M3.1 excludes:

- Parser consumer implementation.
- Chunk table population beyond schema readiness if needed by M3.2.
- Embedding calls and Milvus writes.
- Version visibility switching to `READY`.
- Product knowledge query APIs.
- Admin UI.

## API and Identity

The Gateway exposes:

```text
POST /api/v1/knowledge/documents
```

The request is authenticated with the existing JWT middleware. MVP does not yet implement operator roles, so M3.1 treats authenticated users as allowed upload callers and records `created_by_user_id` for audit. Later M5 operator authorization can narrow this route without changing the document metadata contract.

Request fields:

```json
{
  "product_id": 1001,
  "doc_type": "FAQ",
  "file_name": "laptop-faq.md",
  "content_type": "text/markdown",
  "content_base64": "IyBGQVEK..."
}
```

Response fields:

```json
{
  "document_no": "doc_...",
  "product_id": 1001,
  "doc_type": "FAQ",
  "version": 1,
  "status": "PENDING"
}
```

MVP uses base64 payloads for the service contract to avoid multipart handling inside zRPC. The Gateway may accept JSON only in M3.1. File size is capped by service configuration; the default implementation target is 2 MiB so tests and local demos remain deterministic.

## Upload Flow

1. Gateway authenticates the user and forwards `x-user-id`, bearer metadata, and trace metadata to knowledge-service.
2. knowledge-service validates `product_id`, `doc_type`, file name, content type, decoded size, and base64 payload.
3. The service computes `source_hash = SHA-256(content)` and asks the repository for the next version for `(product_id, doc_type)`.
4. The service stores the original file in MinIO under a deterministic prefix:

   ```text
   knowledge/products/{product_id}/{doc_type}/v{version}/{source_hash}-{sanitized_file_name}
   ```

5. In one `knowledge_db` transaction, the repository inserts `knowledge_documents(status=PENDING)` and a `knowledge.document.ingest` Outbox event.
6. If the DB transaction fails after MinIO succeeds, the service returns a stable internal error and attempts best-effort deletion of the just-written object. The DB remains the fact source; an object without metadata is ignored.
7. If the same `(product_id, doc_type, source_hash)` already exists, the service returns the existing document metadata instead of creating a new version or event.

## Event Contract

Topic: `knowledge.document.ingest`

Key: `document_no`

Payload:

```json
{
  "event_id": "uuid",
  "event_type": "knowledge.document.ingest",
  "document_no": "doc_...",
  "document_id": 123,
  "product_id": 1001,
  "doc_type": "FAQ",
  "version": 1,
  "object_key": "knowledge/products/1001/FAQ/v1/...",
  "source_hash": "sha256hex",
  "payload_version": 1
}
```

`event_id` is generated once during the upload transaction and is reused by any retry. Consumers must treat `(event_id, consumer_group)` as the idempotency key.

## Outbox Worker

The worker mirrors the M2 confirmation outbox:

- Lease `PENDING` rows whose `next_retry_at` is null or due, and stale `PROCESSING` rows whose lease expired.
- Publish with `kafka-go` using synchronous acknowledgements.
- Mark `PUBLISHED` only after Kafka acknowledges.
- On publish failure, return the row to `PENDING`, set `next_retry_at` with capped exponential backoff, and persist a short `last_error` classification.
- After the max attempt threshold, mark `DEAD` and retain the payload for replay or inspection.

The worker does not publish inside the upload transaction.

## Error Handling

User-visible errors use stable application codes:

- invalid doc type, empty file, oversized file, invalid base64: `INVALID_ARGUMENT`
- duplicate upload with same hash: success with the existing document
- MinIO timeout or Kafka timeout: `DEPENDENCY_TIMEOUT`
- MinIO write failure or DB failure: `INTERNAL`

Raw object keys and dependency bodies are not exposed in user-facing errors. Logs must not include document content, JWTs, MinIO credentials, or full request bodies.

## Validation Strategy

Required automated validation:

- Schema contract tests assert `knowledge_documents`, `outbox_events`, `event_consumptions`, `embedding_tasks`, fixed doc type checks, uniqueness constraints, and Outbox indexes.
- Service tests cover valid upload, invalid doc type, invalid base64, oversized content, duplicate source hash replay, and MinIO success followed by DB rollback cleanup attempt.
- Repository tests cover transaction atomicity: document and Outbox are committed together, and insert failure rolls both back.
- Outbox worker tests cover publish success, publish failure retry, stale lease reclaim, and max-attempt `DEAD`.
- Gateway handler tests cover authenticated upload, unauthenticated rejection, and stable error mapping.

Baseline validation before commit:

```text
gofmt -w <changed Go files>
go test ./services/knowledge-service/... ./apps/gateway/... ./internal/platform/... -count=1
go test ./... -count=1
go vet ./...
git diff --check
```

An opt-in Docker integration test with real MySQL and MinIO is useful but not required for the first M3.1 unit-test milestone. If added, it must use a dedicated Compose project, non-default host ports, UUID guard rows, and explicit `AI_SHOPPING_KNOWLEDGE_UPLOAD_INTEGRATION=1`.
