# M3.2 Knowledge Processing and Retrieval Design

## Goal

M3.2 completes the asynchronous RAG ingestion path after M3.1 upload: a `knowledge.document.ingest` event parses the original MinIO object into idempotent chunks, a `knowledge.chunk.embed` event generates embeddings and upserts vectors, and product knowledge retrieval returns only current `READY` versions with source metadata.

Upload remains asynchronous. `POST /api/v1/knowledge/documents` continues to return `PENDING` and never waits for parsing, embedding, or Milvus.

## Current Behavior

M3.1 provides document metadata, MinIO upload, `knowledge.document.ingest` Outbox publication, and a zRPC upload API. `knowledge_documents` already has `PENDING`, `PROCESSING`, `READY`, and `FAILED` statuses plus `chunk_count`, `embedding_model`, and error fields.

The current event payload includes `document_no`, `product_id`, `doc_type`, `version`, `object_key`, and `source_hash`. Its `document_id` field is not populated at event creation time, so M3.2 consumers must treat `document_no` as the stable lookup key and ignore missing or zero `document_id`.

No parser consumer, chunk table, embedding provider, vector store adapter, version visibility logic, or retrieval RPC exists yet.

## Scope

M3.2 includes:

- `knowledge_chunks` schema and migration.
- Document ingest consumer service that:
  - records `(event_id, consumer_group)` idempotency,
  - loads the document by `document_no`,
  - reads the source object from MinIO,
  - parses supported text files,
  - normalizes and splits text into chunks,
  - writes chunks idempotently,
  - creates one durable `knowledge.chunk.embed` Outbox event in the same transaction as chunk persistence,
  - marks invalid or unrecoverable documents as `FAILED`.
- Chunk embed consumer service that:
  - records `(event_id, consumer_group)` idempotency,
  - creates or reuses an `embedding_tasks` row,
  - embeds all chunks for a document,
  - upserts vectors through a `VectorStore` interface,
  - marks chunks `EMBEDDED`,
  - atomically marks the document `READY` only after all chunks and vectors are written.
- Version visibility rules:
  - each `(product_id, doc_type)` has at most one current `READY` version for retrieval,
  - old chunks remain in MySQL for audit but normal retrieval filters them out,
  - if a newer document fails, the previous current `READY` version remains retrievable.
- Product knowledge retrieval gRPC that returns snippets with `doc_type`, `version`, `section`, `source_page`, and similarity score.
- Configurable Embedding model:
  - default provider: Alibaba DashScope,
  - default model: `text-embedding-v4`,
  - default dimension: `1024`,
  - upgrade path to higher supported dimensions such as `1536` or `2048` without changing domain code, but Milvus collections must be rebuilt when dimension changes.

M3.2 excludes:

- Full PDF/Office parser fidelity.
- Real answer generation from retrieved snippets.
- Agent Tool wiring; M4 will call the retrieval RPC.
- Operator UI for retries.
- Model billing, model cost tracking, or multi-provider routing.

## Data Model

Add `knowledge_chunks`:

```text
knowledge_chunks(
  id BIGINT UNSIGNED PK,
  document_id BIGINT UNSIGNED NOT NULL,
  product_id BIGINT UNSIGNED NOT NULL,
  doc_type VARCHAR(32) NOT NULL,
  version INT UNSIGNED NOT NULL,
  chunk_index INT UNSIGNED NOT NULL,
  section VARCHAR(255) NULL,
  source_page INT UNSIGNED NULL,
  content TEXT NOT NULL,
  content_hash CHAR(64) NOT NULL,
  vector_ref VARCHAR(128) NULL,
  status VARCHAR(32) NOT NULL,
  created_at DATETIME(3) NOT NULL,
  updated_at DATETIME(3) NOT NULL,
  UNIQUE(document_id, chunk_index),
  UNIQUE(document_id, content_hash),
  KEY(product_id, doc_type, version, status, chunk_index)
)
```

Chunk statuses:

```text
PENDING_EMBEDDING -> EMBEDDED
PENDING_EMBEDDING -> FAILED
```

Add current-ready marker fields to `knowledge_documents`:

```text
is_current_ready TINYINT(1) NOT NULL DEFAULT 0
ready_at DATETIME(3) NULL
```

The document status remains the lifecycle state. `is_current_ready` is the retrieval visibility marker. This avoids hiding the previous version while a newer version is `PENDING`, `PROCESSING`, or `FAILED`.

Indexes:

```text
KEY idx_knowledge_document_current (product_id, doc_type, is_current_ready, ready_at)
UNIQUE KEY uq_knowledge_document_current_ready (product_id, doc_type, is_current_ready)
```

MySQL cannot express a partial unique index directly, so the implementation must avoid a plain unique key on `(product_id, doc_type, is_current_ready)` because many non-current rows would conflict. Use transaction logic instead: when marking document `READY`, update existing current rows for the same `(product_id, doc_type)` to `is_current_ready = 0`, then update the new document to `is_current_ready = 1`.

## Event Contracts

### `knowledge.document.ingest`

Topic: `knowledge.document.ingest`

Key: `document_no`

Consumer group: `knowledge-document-ingest-v1`

Payload version 1:

```json
{
  "event_id": "uuid",
  "event_type": "knowledge.document.ingest",
  "document_no": "doc_...",
  "document_id": 0,
  "product_id": 1001,
  "doc_type": "FAQ",
  "version": 1,
  "object_key": "knowledge/products/1001/FAQ/v1/...",
  "source_hash": "sha256hex",
  "payload_version": 1
}
```

Consumer behavior:

1. Insert `(event_id, knowledge-document-ingest-v1)` into `event_consumptions`; if duplicate succeeded consumption exists, ack without reprocessing.
2. Load document by `document_no`.
3. If document is already `READY`, ack.
4. If document is `FAILED`, ack only when the failed reason is unrecoverable input. Recoverable dependency failures are retried by returning an error.
5. Transition `PENDING -> PROCESSING`.
6. Parse, normalize, split, and persist chunks.
7. Insert `knowledge.chunk.embed` Outbox event in the same transaction as chunks.
8. Mark consumption `SUCCEEDED`.

### `knowledge.chunk.embed`

Topic: `knowledge.chunk.embed`

Key: `document_no`

Consumer group: `knowledge-chunk-embed-v1`

Payload version 1:

```json
{
  "event_id": "uuid",
  "event_type": "knowledge.chunk.embed",
  "document_no": "doc_...",
  "document_id": 123,
  "product_id": 1001,
  "doc_type": "FAQ",
  "version": 1,
  "chunk_count": 4,
  "embedding_model": "text-embedding-v4",
  "embedding_dimension": 1024,
  "payload_version": 1
}
```

Consumer behavior:

1. Insert `(event_id, knowledge-chunk-embed-v1)` into `event_consumptions`; if duplicate succeeded consumption exists, ack.
2. Create or reuse `embedding_tasks(event_id, document_id, version)`.
3. Load chunks for the document in `chunk_index` order.
4. Call `EmbeddingProvider.EmbedDocuments`.
5. Upsert vectors through `VectorStore.UpsertChunks`.
6. In one DB transaction:
   - set chunk `status = EMBEDDED` and `vector_ref`,
   - mark embedding task `DONE`,
   - clear previous current-ready documents for the same `(product_id, doc_type)`,
   - mark this document `READY`, `is_current_ready = 1`, `ready_at = now`, `embedding_model`, `chunk_count`, `processed_at`.
7. Mark consumption `SUCCEEDED`.

If embedding or vector upsert fails, update `embedding_tasks` retry metadata and return an error so Kafka retry can redeliver. Do not mark the document `FAILED` on the first dependency failure. Mark `FAILED` only when retry policy or explicit dead-letter handling decides no more retries are allowed.

## Parsing and Chunking

MVP parser support:

- `text/plain`
- `text/markdown`
- `application/json` as text

Unsupported content types mark the document `FAILED` with `UNSUPPORTED_CONTENT_TYPE` and do not create chunks.

Normalization:

- convert CRLF/CR to LF,
- trim surrounding whitespace,
- collapse runs of blank lines to at most two,
- remove NUL bytes.

Chunking:

- target size: 900 characters,
- hard max: 1200 characters,
- split first by Markdown headings, then paragraphs, then hard split long sections,
- `section` is the latest Markdown heading text without leading `#`; when absent, use file name,
- `source_page` is `NULL` for text formats in M3.2.

Empty normalized content marks the document `FAILED` with `EMPTY_CONTENT`.

## Embedding and Vector Store Interfaces

Domain code depends on small interfaces:

```go
type EmbeddingProvider interface {
	EmbedDocuments(ctx context.Context, input EmbeddingInput) (EmbeddingOutput, error)
}

type VectorStore interface {
	UpsertChunks(ctx context.Context, input VectorUpsertInput) error
	Search(ctx context.Context, input VectorSearchInput) ([]VectorSearchHit, error)
}
```

The DashScope adapter is runtime wiring. Unit tests use fake providers or `httptest` and never call external services.

Milvus records must carry:

```text
chunk_id, product_id, document_id, doc_type, version, is_current_ready, embedding_model
```

Retrieval must still check MySQL current-ready metadata after vector search. Milvus metadata filtering is a performance and relevance optimization, not the sole correctness boundary.

## Retrieval RPC

Add RPC:

```text
SearchProductKnowledge(SearchProductKnowledgeRequest) returns (SearchProductKnowledgeResponse)
```

Request:

```text
product_id uint64
query string
doc_types []string
top_k uint32
```

Response:

```text
snippets[] {
  chunk_id uint64
  document_no string
  product_id uint64
  doc_type string
  version uint32
  section string
  source_page uint32
  content string
  score double
}
fallback_reason string
```

Rules:

- `product_id` and non-empty `query` are required.
- `top_k` defaults to 5 and is capped at 10.
- If no current `READY` documents exist, return an empty snippet list and `fallback_reason = "NO_READY_KNOWLEDGE"`.
- If embedding or vector search times out, return a stable dependency timeout error to callers. Agent-facing controlled fallback is implemented in M4 by the Tool layer.
- Retrieval never returns chunks from old versions.

## Error Handling

Stable internal error classes:

- `UNSUPPORTED_CONTENT_TYPE`
- `EMPTY_CONTENT`
- `PARSE_FAILED`
- `EMBEDDING_FAILED`
- `VECTOR_UPSERT_FAILED`
- `VECTOR_SEARCH_FAILED`
- `DEPENDENCY_TIMEOUT`

Raw model responses, MinIO object data, Kafka message bodies, and vector store error bodies must not be returned to users.

## Validation Strategy

Required automated validation:

- Schema contract test for `knowledge_chunks`, current-ready fields, chunk indexes, and status checks.
- Chunker tests for Markdown headings, long paragraph split, blank content, CRLF normalization, and content hash stability.
- Ingest service tests for duplicate consume, unsupported content type failure, chunk idempotency, and creation of exactly one `knowledge.chunk.embed` event.
- Embed service tests for duplicate consume, embedding retry, vector upsert failure, successful `READY` transition, and previous version remaining current when a new version fails.
- Retrieval tests for current-ready filtering, old version exclusion, top-k cap, no-evidence fallback, and dependency timeout mapping.
- Transport tests for the new gRPC search method.

Baseline validation before M3.2 commit:

```text
gofmt -w services/knowledge-service api/knowledge
go test ./services/knowledge-service/... -count=1
go test ./... -count=1
go vet ./...
git diff --check
```

Real DashScope, Milvus, Kafka, MinIO, and MySQL integration tests are explicitly gated by environment variables. They must not run during normal `go test ./...`. The M3.2 harness uses project `m32knowledge`, a UUID `knowledge_db.knowledge_integration_guards` row, loopback non-`3306` MySQL validation, and `AI_SHOPPING_KNOWLEDGE_M32_INTEGRATION=1` before it can start Docker or call DashScope.
