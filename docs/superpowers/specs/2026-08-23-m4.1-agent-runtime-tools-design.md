# M4.1 Agent Runtime and Controlled Tools Design

## Goal

M4.1 establishes the `agent-service` runtime foundation: sessions, messages, runs, steps, controlled Tool execution, model-provider boundaries, and stable failure states. It makes an Agent run observable and bounded, but leaves final recommendation snapshot validation to M4.2.

## Current Behavior

`agent-service` is currently only an executable skeleton with config loading. `agent_db` is reserved by `deploy/mysql/init/04-agent-schema.sql`, but it has no tables. Gateway has no Agent API. Product, user, and knowledge services already expose the read RPCs needed for the first Tool set:

- `product-service.ListProducts`
- `product-service.GetProduct`
- `product-service.GetCheckoutSKUs`
- `user-service.GetMyProfile`
- `knowledge-service.SearchProductKnowledge`

## Scope

M4.1 includes:

- `agent_sessions`, `agent_messages`, `agent_runs`, and `agent_steps` schema plus migration.
- Agent domain state machine:
  - `AgentRun`: `RUNNING -> SUCCEEDED | FAILED | TIMEOUT`
  - `AgentStep`: `RUNNING -> SUCCEEDED | FAILED | TIMEOUT`
  - maximum 8 steps per run,
  - maximum 30 seconds wall-clock per run,
  - every external dependency call uses `context.Context` timeout.
- Agent RPC contract:
  - `StartRun` creates a session if needed, persists the user message, starts a bounded run, and returns the run result for M4.1 synchronous tests.
  - `GetRun` returns run state, messages, and ordered step timeline.
- Controlled Tool registry:
  - `search_products`
  - `get_user_profile`
  - `get_price_stock`
  - `get_discount`
  - `search_product_knowledge`
- Tool definitions include name, JSON input schema, timeout, max result count, permission source, and stable output DTO.
- Server-side user identity injection:
  - `get_user_profile` and `get_discount` never trust model-supplied `user_id`,
  - the current user ID comes from verified JWT metadata.
- Model provider abstraction:
  - domain code depends on `ChatModel` and `ToolCall` interfaces,
  - Eino/DashScope/OpenAI-compatible provider details are isolated behind an adapter package,
  - unit tests use fakes and never call real LLM providers.
- Error taxonomy:
  - `INVALID_TOOL_ARGUMENT`
  - `UNKNOWN_TOOL`
  - `TOOL_TIMEOUT`
  - `TOOL_FAILED`
  - `MAX_STEPS_EXCEEDED`
  - `MODEL_FAILED`
  - `DEPENDENCY_TIMEOUT`

M4.1 excludes:

- Final recommendation output schema and immutable recommendation snapshots.
- Price/stock/discount second-pass validation before writing `recommendations`.
- SSE streaming.
- Gateway HTTP Agent endpoints.
- Operator UI for Run timeline.
- Real multi-provider routing, model cost tracking, or billing.

## Data Model

Add to `agent_db`:

```text
agent_sessions(
  id BIGINT UNSIGNED PK,
  session_no VARCHAR(64) UNIQUE NOT NULL,
  user_id BIGINT UNSIGNED NOT NULL,
  title VARCHAR(255) NOT NULL,
  status VARCHAR(32) NOT NULL,
  created_at DATETIME(3) NOT NULL,
  updated_at DATETIME(3) NOT NULL,
  KEY(user_id, updated_at)
)

agent_messages(
  id BIGINT UNSIGNED PK,
  session_id BIGINT UNSIGNED NOT NULL,
  seq_no INT UNSIGNED NOT NULL,
  role VARCHAR(32) NOT NULL,
  content TEXT NOT NULL,
  model_name VARCHAR(128) NULL,
  prompt_version VARCHAR(64) NULL,
  token_usage_json JSON NULL,
  created_at DATETIME(3) NOT NULL,
  UNIQUE(session_id, seq_no),
  KEY(session_id, created_at)
)

agent_runs(
  id BIGINT UNSIGNED PK,
  run_id VARCHAR(64) UNIQUE NOT NULL,
  session_id BIGINT UNSIGNED NOT NULL,
  user_id BIGINT UNSIGNED NOT NULL,
  trace_id VARCHAR(64) UNIQUE NOT NULL,
  user_input TEXT NOT NULL,
  status VARCHAR(32) NOT NULL,
  model_name VARCHAR(128) NOT NULL,
  prompt_version VARCHAR(64) NOT NULL,
  step_count INT UNSIGNED NOT NULL DEFAULT 0,
  final_result_json JSON NULL,
  error_code VARCHAR(64) NULL,
  error_message VARCHAR(255) NULL,
  started_at DATETIME(3) NOT NULL,
  ended_at DATETIME(3) NULL,
  created_at DATETIME(3) NOT NULL,
  KEY(user_id, created_at),
  KEY(session_id, created_at),
  KEY(status, created_at)
)

agent_steps(
  id BIGINT UNSIGNED PK,
  run_id BIGINT UNSIGNED NOT NULL,
  step_no INT UNSIGNED NOT NULL,
  step_type VARCHAR(32) NOT NULL,
  tool_name VARCHAR(64) NULL,
  attempt INT UNSIGNED NOT NULL DEFAULT 1,
  input_json JSON NULL,
  output_json JSON NULL,
  status VARCHAR(32) NOT NULL,
  error_code VARCHAR(64) NULL,
  error_message VARCHAR(255) NULL,
  latency_ms INT UNSIGNED NOT NULL DEFAULT 0,
  started_at DATETIME(3) NOT NULL,
  ended_at DATETIME(3) NULL,
  UNIQUE(run_id, step_no, attempt),
  KEY(run_id, step_no)
)
```

`recommendations` is created in M4.2 because M4.1 does not yet accept final SKU rankings.

## Agent Run Flow

1. Verify JWT and extract current user ID.
2. Create or load `agent_sessions`.
3. Append the user message with next `seq_no`.
4. Create `agent_runs(status=RUNNING)` with `run_id`, `trace_id`, `model_name`, and `prompt_version`.
5. Loop until the model returns a final text result or a terminal error:
   - cap steps at 8,
   - create `agent_steps(status=RUNNING)` before each model/tool action,
   - validate tool name and JSON arguments against registry schema,
   - execute the Tool with its own timeout,
   - persist sanitized input/output or stable error,
   - feed successful Tool output back into the next model turn.
6. Mark run `SUCCEEDED`, `FAILED`, or `TIMEOUT`.

The run loop must never leave a `RUNNING` step without a terminal state.

## Tool Contracts

### `search_products`

Input:

```json
{
  "keyword": "laptop",
  "category_id": 0,
  "budget_min": "3000.00",
  "budget_max": "5000.00",
  "limit": 5
}
```

Rules:

- `limit` defaults to 5 and caps at 10.
- Tool maps to `product-service.ListProducts`.
- Output contains product IDs, title, min price, stock status, and match fields.

### `get_user_profile`

Input:

```json
{}
```

Rules:

- Any model-supplied `user_id` is ignored or rejected.
- Tool maps to `user-service.GetMyProfile` with caller JWT metadata.

### `get_price_stock`

Input:

```json
{
  "sku_ids": [10001, 10002]
}
```

Rules:

- `sku_ids` must be non-empty and capped at 20.
- Tool maps to `product-service.GetCheckoutSKUs`.
- Output contains SKU ID, product ID, saleable, sale price, spec JSON, and stock status.

### `get_discount`

Input:

```json
{
  "sku_ids": [10001, 10002]
}
```

Rules:

- M4.1 reuses `product-service.GetCheckoutSKUs` promotion summaries.
- User-specific coupon qualification can be added after user coupon RPC exists.
- The current user ID is still injected into the Tool context for future compatibility.

### `search_product_knowledge`

Input:

```json
{
  "product_id": 1001,
  "query": "battery warranty",
  "doc_types": ["FAQ", "AFTER_SALE"],
  "top_k": 5
}
```

Rules:

- `product_id` and non-empty `query` are required.
- `top_k` defaults to 5 and caps at 10.
- Tool maps to `knowledge-service.SearchProductKnowledge`.
- If M3.2 returns `NO_READY_KNOWLEDGE`, Tool returns a controlled fallback instead of inventing an answer.

## Security and Privacy

- JWT, model API keys, and internal service tokens come only from environment variables or secret management.
- `agent_steps.input_json` and `output_json` store sanitized JSON only.
- Raw provider bodies, authorization headers, phone numbers, addresses, and payment fields are not persisted.
- Tool SQL is impossible by construction: Tools only call typed gRPC clients or in-memory fakes in tests.

## Validation Strategy

Required automated validation:

- Schema contract test for `agent_sessions`, `agent_messages`, `agent_runs`, `agent_steps`, state checks, indexes, and uniqueness.
- Run service tests for success, model failure, tool timeout, invalid tool argument, unknown tool, max step cap, and run timeout.
- Tool registry tests for all tool definitions, schemas, max result caps, and user ID injection behavior.
- Tool adapter tests using fake gRPC clients for product, user, and knowledge calls.
- Server tests for JWT auth, `StartRun`, `GetRun`, invalid request mapping, and stable error messages.

Baseline validation before M4.1 commits:

```text
gofmt -w services/agent-service api/agent
go test ./services/agent-service/... -count=1
go test ./... -count=1
go vet ./...
git diff --check
```
