# M4.2 Recommendation Snapshot and Verification Design

## Goal

M4.2 makes Agent recommendations trustworthy and replayable. The model may propose SKU IDs, ranks, and reasons, but `agent-service` must re-check price, saleability, SKU metadata, and promotion summaries through controlled backend reads before it writes immutable recommendation snapshots.

## Current Behavior

M4.1 provides:

- `agent_sessions`, `agent_messages`, `agent_runs`, and `agent_steps`.
- A bounded `RunService` with `ChatModel`, `ToolRunner`, and `ToolRegistry` boundaries.
- Read-only Tools backed by product, user, and knowledge clients.
- `StartRun` and `GetRun` gRPC, where `GetRun` returns the run and ordered step timeline.

M4.1 deliberately does not define a final recommendation schema, does not create `recommendations`, and uses a disabled model provider in runtime wiring.

## Scope

M4.2 includes:

- A strict model final-output schema:

```json
{
  "recommendations": [
    {
      "sku_id": 2001,
      "rank_no": 1,
      "reason": "适合编程和轻度游戏"
    }
  ]
}
```

- Server-side validation that accepts only SKU ID, rank, and reason from the model. Any model-supplied price, stock, saleability, spec, discount, product title, user ID, or order field is ignored.
- A `recommendations` table in `agent_db` storing immutable backend-verified snapshots.
- A recommendation verifier that calls the existing product read surface to re-fetch candidate SKUs before persistence.
- Run completion that succeeds only when at least one recommended SKU survives verification.
- `GetRun` response extension to include recommendation snapshots.
- Tests for nonexistent SKU, unsaleable SKU, duplicate rank/SKU, model-forged trade fields, promotion changes, and the no-valid-recommendation failure path.

M4.2 excludes:

- Real Eino or LLM provider integration.
- Prompt engineering and provider routing.
- SSE streaming and Gateway HTTP Agent endpoints.
- Cart/order writes from Agent recommendations.
- User coupon qualification beyond existing product promotion summaries.

## Data Model

Add to `agent_db`:

```text
recommendations(
  id BIGINT UNSIGNED PK,
  run_id BIGINT UNSIGNED NOT NULL,
  rank_no INT UNSIGNED NOT NULL,
  sku_id BIGINT UNSIGNED NOT NULL,
  product_id BIGINT UNSIGNED NOT NULL,
  product_title_snapshot VARCHAR(255) NOT NULL,
  sku_code_snapshot VARCHAR(128) NOT NULL,
  sku_spec_snapshot_json JSON NOT NULL,
  price_snapshot DECIMAL(12,2) NOT NULL,
  saleable_snapshot TINYINT(1) NOT NULL,
  discount_snapshot_json JSON NOT NULL,
  reason VARCHAR(512) NOT NULL,
  validation_status VARCHAR(32) NOT NULL,
  created_at DATETIME(3) NOT NULL,
  UNIQUE(run_id, rank_no),
  UNIQUE(run_id, sku_id),
  KEY(run_id, rank_no),
  CHECK(validation_status IN ('VERIFIED'))
)
```

`run_id` is the internal numeric `agent_runs.id`, not the public `agent_runs.run_id` string. There are no cross-service physical foreign keys to product tables; product and SKU IDs are immutable snapshot references owned by `product-service`.

## Domain Model

Add model-final DTOs to `agent-service/internal/agent`:

```go
type FinalRecommendationOutput struct {
	Recommendations []ModelRecommendation `json:"recommendations"`
}

type ModelRecommendation struct {
	SKUID  uint64 `json:"sku_id"`
	RankNo uint32 `json:"rank_no"`
	Reason string `json:"reason"`
}
```

Validation rules:

- `recommendations` must be non-empty.
- `sku_id` and `rank_no` must be positive.
- `rank_no` must be unique.
- `sku_id` must be unique.
- `reason` must be non-empty after trimming and capped at 512 runes.
- Unknown fields are rejected when parsing model final output. This prevents forged `price`, `stock`, `discount`, `saleable`, `user_id`, or write-intent fields from entering the domain silently.
- The maximum accepted recommendation candidates is 10. This matches Tool result caps and keeps verification bounded.

## Verification Flow

When the model returns final recommendations:

1. Parse final JSON with `json.Decoder.DisallowUnknownFields`.
2. Validate rank/SKU/reason shape.
3. Collect unique SKU IDs in rank order.
4. Call `ProductClient.GetCheckoutSKUs(ctx, skuIDs)` with the existing Tool timeout.
5. Build a map by SKU ID from backend response.
6. For each model candidate in rank order:
   - drop it if the backend did not return the SKU,
   - drop it if `saleable=false`,
   - use backend `product_id`, `product_title`, `sku_code`, `spec_json`, `sale_price`, and `promotions`,
   - persist a snapshot with `validation_status='VERIFIED'`.
7. If no candidates survive, terminally mark the run as `FAILED` with `NO_VALID_RECOMMENDATION`.
8. If at least one candidate survives, write all verified snapshots and mark the run `SUCCEEDED`.

M4.2 may perform verification with one batched product call. Additional concurrency is not needed because `GetCheckoutSKUs` already accepts a SKU list; this is simpler and keeps failure semantics atomic.

## Persistence Boundary

Extend the repository with:

```go
SaveRecommendations(ctx context.Context, runDBID uint64, items []RecommendationSnapshot) error
ListRecommendations(ctx context.Context, runDBID uint64) ([]RecommendationSnapshot, error)
```

`SaveRecommendations` inserts all snapshots in one `agent_db` transaction. It is called before `MarkRunSucceeded`; if snapshot insertion fails, the run must not be marked successful. `ListRecommendations` is used by `GetRunTimeline`.

The run service remains the only writer of recommendation snapshots. Tools and model adapters cannot write recommendations directly.

## API Contract

Extend `api/agent/agent.proto`:

```text
message GetRunResponse {
  AgentRun run = 1;
  repeated AgentStep steps = 2;
  repeated Recommendation recommendations = 3;
}

message Recommendation {
  uint32 rank_no = 1;
  uint64 sku_id = 2;
  uint64 product_id = 3;
  string product_title = 4;
  string sku_code = 5;
  bytes sku_spec_json = 6;
  string price = 7;
  bool saleable = 8;
  bytes discount_json = 9;
  string reason = 10;
  string validation_status = 11;
}
```

`StartRunResponse` can return the same `AgentRun` summary as M4.1. `GetRun` is the replay API for recommendation snapshots and ordered steps.

## Error Taxonomy

Add stable domain error:

```text
NO_VALID_RECOMMENDATION
```

Mapping:

- Invalid final JSON or schema violation: `INVALID_FINAL_RECOMMENDATION`
- Backend verification timeout: `DEPENDENCY_TIMEOUT`
- Backend verification failure: `TOOL_FAILED`
- No valid SKU after filtering: `NO_VALID_RECOMMENDATION`

Provider/raw dependency bodies are not persisted or returned. Error messages remain short:

- `invalid final recommendation`
- `dependency timeout`
- `tool execution failed`
- `no valid recommendation`

## Security and Privacy

- Model final output cannot set user ID, price, stock, discount, saleability, order, wallet, SQL, or metadata fields.
- Recommendation snapshots contain product/SKU data, price, spec, promotions, and model reason only; no address, phone, wallet, JWT, API key, or raw provider body is stored.
- `GetRun` remains owner-scoped through JWT-derived user ID.
- `agent_steps` continue storing sanitized model/tool input and output. M4.2 does not widen retention or logging scope.

## Validation Strategy

Required automated checks:

- Schema contract test asserts `recommendations`, uniqueness, JSON snapshot columns, decimal price, and `VERIFIED` check.
- Final output parser tests cover valid output, unknown forged fields, empty recommendations, duplicate SKU/rank, invalid reason, and candidate cap.
- Recommendation verifier tests cover:
  - successful snapshot from backend fields,
  - nonexistent SKU filtered,
  - unsaleable SKU filtered,
  - model-forged price ignored,
  - changed promotions persisted from backend response,
  - no valid recommendation returns `NO_VALID_RECOMMENDATION`.
- Repository tests cover atomic insert/list and owner-scoped timeline loading with recommendations.
- Run service tests cover final recommendation success and no-valid-recommendation failure.
- Server tests cover `GetRun` returning recommendations without leaking unowned runs.

Baseline validation:

```text
gofmt -w services/agent-service api/agent
go test ./services/agent-service/... -count=1
go test ./... -count=1
go vet ./...
git diff --check
```

## Milestone Boundary

M4.2 is complete when a fake model can return structured recommendation candidates, `agent-service` validates and re-checks them against product-service snapshots, persists only verified recommendations, and `GetRun` can replay the run, steps, and final recommendation snapshots. A real model provider remains a later phase so provider compatibility does not obscure snapshot correctness.
