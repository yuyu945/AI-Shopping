# M5.1c User App Experience Design

## Goal

M5.1c adds the first real user-facing web app for 智选购 so a user can operate the MVP shopping path through Gateway HTTP/SSE: product discovery, product detail with SKU switching and knowledge Q&A, cart, order creation, wallet payment recovery, order detail, review submission, and AI guide recommendations.

## Current Behavior

The backend already exposes the user-facing contracts needed by this slice:

- Auth: `POST /api/v1/auth/register`, `POST /api/v1/auth/login`.
- User profile and addresses: `GET/POST /api/v1/users/me/profile`, `GET/POST /api/v1/users/me/addresses`.
- Products: `GET /api/v1/products`, `GET /api/v1/products/{id}` with optional `sku_id`.
- Cart and orders: `GET /api/v1/cart`, `POST /api/v1/cart/items`, `PUT/DELETE /api/v1/cart/items/{id}`, `GET/POST /api/v1/orders`, `GET /api/v1/orders/{order_no}`, `POST /api/v1/orders/{order_no}/payments/wallet`.
- Reviews: `POST /api/v1/orders/{order_no}/items/{sku_id}/reviews`.
- Agent guide: `POST /api/v1/agent/runs`, `GET /api/v1/agent/runs/{run_id}`, `GET /api/v1/agent/runs/{run_id}/events`.
- Product knowledge Q&A: `POST /api/v1/products/{product_id}/knowledge/questions`.

No frontend app exists in the repository. There is no `package.json`, Vite, Next.js, React, or browser test setup. The Gateway contracts are currently verified through Go handler tests and service tests, not by a browser workflow.

## Scope

M5.1c includes:

- Create a minimal React + TypeScript + Vite app under `apps/web`.
- Add an API client that stores the bearer token locally, forwards `Authorization`, handles stable Gateway error codes, and supports SSE replay from Agent runs.
- Implement user app routes:
  - Login/register.
  - Product list with keyword search and direct AI guide handoff for natural-language searches.
  - Product detail with SKU switching, price/stock/promotion display, add-to-cart, and product knowledge Q&A with sources.
  - Cart.
  - Order confirmation using existing selected-cart create-order behavior.
  - Wallet payment with submit-in-progress, timeout recovery by order lookup, out-of-stock, insufficient-balance, and payment-in-progress states.
  - Order list and order detail.
  - Review form for paid order items.
  - AI guide page with run creation, SSE replay events, step timeline, verified recommendation cards, and controlled failure messages.
- Add frontend unit/component tests for stateful client logic and key page behavior.
- Add `README.md` and `.env.example` updates for local web app execution.
- Update `docs/TASKS.md` after the slice is verified.

M5.1c excludes:

- Operations console pages.
- Knowledge document list/upload/retry UI.
- Agent Run admin list or Step redacted diagnostic detail.
- `behavior.events`, event overview, retry/dead-letter read models.
- New backend transaction semantics.
- Real LLM provider integration beyond whatever `agent-service` runtime is configured to use.
- A marketing landing page or full design system.

## Architecture

The app will be a Vite single-page app mounted under `apps/web`. It will call the existing Gateway through a configurable `VITE_API_BASE_URL`, defaulting to `http://localhost:8080` for local development. Routing stays client-side with small route components; shared API and domain-state code stays in focused modules so behavior can be tested without a browser.

The app does not become a new backend owner. It never computes prices, stock, discounts, payment results, or recommendation validity as facts. It renders snapshots returned by Gateway and treats network failures as unknown states that require retry or order/run replay.

## Frontend Technology

Use:

- Vite.
- React.
- TypeScript.
- Vitest and React Testing Library.
- Plain CSS modules or a single scoped CSS file with CSS variables.

Do not add a UI kit, global state framework, animation library, or icon package unless implementation finds an existing project dependency. The first version should be compact, operational, and testable.

## Information Architecture

Primary navigation:

- `Products`: product list and detail.
- `AI Guide`: natural-language shopping guide.
- `Cart`: selected cart and checkout entry.
- `Orders`: order list, payment status, detail, review.

Support routes:

- `/login`
- `/register`
- `/products`
- `/products/:productId`
- `/guide`
- `/cart`
- `/checkout`
- `/orders`
- `/orders/:orderNo`

The first viewport should be a usable product or guide workflow, not a landing page. Desktop layouts may use two columns for AI guide and product detail; mobile layouts collapse to a single column with the primary action kept reachable.

## API Client Contract

Create a small client layer with these responsibilities:

- `getToken`, `setToken`, `clearToken`.
- `apiFetch<T>(path, options)`:
  - prefixes `VITE_API_BASE_URL`;
  - sets `Content-Type: application/json` for JSON requests;
  - sets `Authorization: Bearer <token>` when present;
  - parses stable Gateway error bodies shaped like `{code, message}`;
  - maps transport failures to `NETWORK_ERROR`;
  - maps timeout/abort to `REQUEST_TIMEOUT`.
- Endpoint wrappers:
  - `login`, `register`;
  - `listProducts`, `getProduct`;
  - `getCart`, `addCartItem`, `updateCartItem`, `deleteCartItem`;
  - `listAddresses`, `createOrder`, `listOrders`, `getOrder`, `payWallet`;
  - `submitReview`;
  - `startAgentRun`, `getAgentRun`, `subscribeAgentRunEvents`;
  - `askProductQuestion`.

The client layer should expose DTOs matching Gateway JSON names, not generated Go protobuf types.

## User Flow Details

### Products

The product list shows cards with title, subtitle, minimum sale price, stock status, and a detail action. Loading, empty, and dependency-failure states use stable card dimensions to avoid layout shift.

Search supports two paths:

- Short keyword-like input updates product filtering through `GET /api/v1/products?keyword=...`.
- Natural-language purchase intent can be sent to `/guide?message=...` so the AI guide creates an Agent run.

The app may expose this distinction through a segmented control or explicit "Search products" and "Ask AI" actions instead of trying to classify the text automatically.

### Product Detail and Knowledge Q&A

The product detail page renders SKU options from the product response. Selecting a SKU calls `GET /api/v1/products/{id}?sku_id=<sku_id>` and disables cart actions while reloading. The selected SKU's `sale_price`, `stock_qty`, `stock_status`, specs, and promotions are the displayed business facts.

The knowledge Q&A panel calls `POST /api/v1/products/{product_id}/knowledge/questions`. Results display snippets with `doc_type`, `version`, `section`, `source_page`, and content. If `fallback_reason` is non-empty or snippets are empty, the UI shows a controlled message that the materials do not contain enough evidence. It does not generate unsourced answer text.

### Cart and Checkout

The cart page reads `GET /api/v1/cart` and lets users update quantity, selection, and deletion. Because existing cart item DTOs only include `sku_id`, `quantity`, and `selected`, M5.1c can render a compact cart and link back to product detail when product information is available from recent product/recommendation context. It must not invent price totals from incomplete cart DTOs.

Checkout uses `POST /api/v1/orders` with a generated `request_id` and a selected address ID. The order response is the first authoritative checkout snapshot. If order creation times out, the UI must not blindly create another order with a new `request_id`; it keeps the original `request_id` and prompts the user to retry with the same request.

### Payment Recovery

Wallet payment calls `POST /api/v1/orders/{order_no}/payments/wallet`.

UI states:

- `submitting`: disable the payment button and show progress.
- `paid`: render the returned paid order.
- `OUT_OF_STOCK`: keep the order visible and offer cart/product refresh.
- `INSUFFICIENT_BALANCE`: keep the order visible and show a stable balance-related action.
- `PAYMENT_IN_PROGRESS`: poll `GET /api/v1/orders/{order_no}` and show the latest persisted status.
- `DEPENDENCY_TIMEOUT`, `NETWORK_ERROR`, `REQUEST_TIMEOUT`: immediately call `GET /api/v1/orders/{order_no}` before allowing another payment click.

The frontend never marks an order paid unless `GetOrder` or `PayWallet` returns a paid status.

### Orders and Reviews

The order list shows order number, status, total amount, paid amount, and snapshot item titles. The order detail page renders shipping and item snapshots returned by Gateway. A review form is shown for paid orders. Successful review submission updates only local review state; analytics processing remains asynchronous and invisible to the user.

### AI Guide

The guide page accepts a natural-language message and calls `POST /api/v1/agent/runs`. It then opens `GET /api/v1/agent/runs/{run_id}/events`.

SSE event rendering:

- `run_snapshot`: update run header.
- `step_snapshot`: append/update step timeline by `step_no`.
- `recommendation_snapshot`: append/update recommendation cards by `sku_id`.
- `run_completed`: enable recommendation actions.
- `run_failed`: show a stable failure message using `code`.
- `heartbeat`: keep progress visible without inventing new steps.

Recommendation cards visually separate:

- AI reason: `reason`.
- Backend verified facts: `sku_id`, `product_id`, `sku_code`, `sku_spec_json`, `price`, `saleable`, `discount_json`, `validation_status`.
- Actions: view product detail and add SKU to cart.

If SSE fails, the app calls `GET /api/v1/agent/runs/{run_id}` and renders the replay result.

## Error Handling

Use stable user-facing messages derived from Gateway codes:

| Code | User-facing behavior |
| --- | --- |
| `UNAUTHENTICATED` | Clear invalid token and send user to login. |
| `INVALID_ARGUMENT` | Mark the relevant form field or show a short invalid-input message. |
| `NOT_FOUND` | Show resource-not-found state with navigation back. |
| `OUT_OF_STOCK` | Preserve order/cart state and guide the user to refresh or change quantity. |
| `INSUFFICIENT_BALANCE` | Preserve order state and show balance-related guidance. |
| `PAYMENT_IN_PROGRESS` | Disable duplicate payment and replay order status. |
| `AGENT_RUN_FAILED` | Show controlled AI-guide failure and keep the original prompt. |
| `DEPENDENCY_TIMEOUT` | Retry by replaying persisted run/order where possible. |
| `NETWORK_ERROR`, `REQUEST_TIMEOUT` | Treat result as unknown and replay persisted state before resubmission. |

Raw backend messages, stack traces, JWTs, addresses beyond order snapshots, wallet internals, model prompts, and Tool payloads must not be exposed.

## Security and Privacy

- Store the bearer token in local storage for MVP local development only; keep token handling isolated in the client module.
- Never log JWTs or request bodies containing addresses/reviews to the browser console.
- Do not render raw HTML from product `detail_markdown`; display it as plain text in M5.1c. A future sanitizer requires a separate design and test plan.
- Treat review content and knowledge snippets as untrusted text.
- The UI does not accept or send `user_id` for Agent, order, profile, cart, review, or knowledge operations.

## Testing Strategy

Automated frontend tests:

- API client:
  - attaches bearer token;
  - maps Gateway error JSON;
  - maps network and abort failures;
  - keeps DTO JSON field names stable.
- Payment state:
  - timeout triggers order replay before another payment attempt;
  - `PAYMENT_IN_PROGRESS` triggers order replay;
  - `OUT_OF_STOCK` and `INSUFFICIENT_BALANCE` preserve the order snapshot.
- Agent guide state:
  - SSE snapshots build a run timeline;
  - SSE failure falls back to `GetRun`;
  - failed runs keep the prompt and show stable error copy.
- Knowledge Q&A:
  - snippets render source metadata;
  - empty snippets or fallback reason shows no-evidence copy.
- Product detail:
  - SKU switch reload disables cart action;
  - selected SKU fields drive displayed price and stock.

Manual/browser validation:

- Desktop and mobile viewport screenshots for products, detail, guide, cart, checkout/payment, order detail/review.
- Verify no overlapping text, no card resizing from loading/error labels, and keyboard-focusable primary controls.

Repo validation:

```text
npm --prefix apps/web test -- --run
npm --prefix apps/web run build
gofmt -w docs
go test ./apps/gateway/... -count=1
go test ./... -count=1
go vet ./...
git diff --check
```

## Milestone Boundary

M5.1c is complete when a local browser can use the new web app to run the user-facing MVP path through existing Gateway endpoints: authenticate, browse products, ask product knowledge questions with sources, run the AI guide and replay SSE recommendations, add a recommended SKU to cart, create an order, handle wallet payment success/failure/recovery states, view the order, and submit a review.

This slice proves the user experience and recovery states. It does not complete the operations console or behavior event analytics, which remain separate M5.2 follow-up slices.
