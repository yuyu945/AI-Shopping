# M5.2a Review Event Outbox Design

## Goal

M5.2a adds the first event-producing user interaction after payment: an authenticated user can submit one review for an owned paid order item, and `order-service` atomically persists the review plus a `review.events` Outbox row.

## Current Behavior

M2 provides:

- User-scoped cart, order creation, order list/detail, wallet payment, and immutable order item snapshots.
- `trade_db.outbox_events` with generic topic, event key, payload, retry, lease, and publish state columns.
- `order-service` Outbox worker for `inventory.reservation.confirm`.

M5.1a and M5.1b added Gateway routes for Agent run replay/SSE and product knowledge questions. There is still no review submission endpoint, review schema, review RPC, or review event producer.

## Scope

M5.2a includes:

- Add `reviews` table in `trade_db`.
- Add `SubmitReview` gRPC to `api/order/order.proto`.
- Add `order.Service.SubmitReview`.
- Add MySQL repository method that inserts `reviews` and `review.events` Outbox in the same transaction.
- Add Gateway client and HTTP route:
  - `POST /api/v1/orders/{order_no}/items/{sku_id}/reviews`
- Add tests for validation, ownership, order status, SKU membership, duplicate review, and Outbox atomicity.
- Record progress in `docs/TASKS.md`.

M5.2a excludes:

- Kafka publisher for `review.events`.
- Analytics consumer, retry/dead-letter handling, or operations event overview.
- Review moderation, media uploads, helpful votes, tags, or replies.
- Frontend review form.
- Product-service aggregate rating updates.

## Data Model

Add to `trade_db`:

```sql
CREATE TABLE reviews (
    id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    review_no VARCHAR(64) NOT NULL,
    order_id BIGINT UNSIGNED NOT NULL,
    order_item_id BIGINT UNSIGNED NOT NULL,
    order_no VARCHAR(64) NOT NULL,
    user_id BIGINT UNSIGNED NOT NULL,
    product_id BIGINT UNSIGNED NOT NULL,
    sku_id BIGINT UNSIGNED NOT NULL,
    rating TINYINT UNSIGNED NOT NULL,
    content VARCHAR(1000) NOT NULL,
    status VARCHAR(32) NOT NULL DEFAULT 'PUBLISHED',
    created_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
    updated_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),
    PRIMARY KEY (id),
    UNIQUE KEY uq_reviews_review_no (review_no),
    UNIQUE KEY uq_reviews_order_item (order_item_id),
    KEY idx_reviews_user_created (user_id, created_at),
    KEY idx_reviews_product_created (product_id, created_at),
    CONSTRAINT chk_reviews_rating_range CHECK (rating BETWEEN 1 AND 5),
    CONSTRAINT fk_reviews_order FOREIGN KEY (order_id) REFERENCES orders(id),
    CONSTRAINT fk_reviews_order_item FOREIGN KEY (order_item_id) REFERENCES order_items(id)
) ENGINE=InnoDB;
```

`uq_reviews_order_item` enforces exactly one review per purchased order item. `order_no`, `product_id`, and `sku_id` are duplicated intentionally as immutable query/event fields copied from the order snapshot.

## Domain Contract

Add domain types:

```go
type Review struct {
	ID, OrderID, OrderItemID, UserID, ProductID, SKUID uint64
	ReviewNo, OrderNo, Content, Status string
	Rating uint32
}

type SubmitReviewInput struct {
	OrderNo string
	SKUID   uint64
	Rating  uint32
	Content string
}
```

Validation:

- `user_id` must come from authenticated transport context.
- `order_no` and `sku_id` are required.
- `rating` must be `1..5`.
- `content` is required after trimming and capped at 1000 runes.
- The order must belong to the current user.
- The order status must be `PAID`.
- The SKU must exist in that order's immutable order items.
- A duplicate review for the same `order_item_id` maps to `IDEMPOTENCY_CONFLICT`.

`PAID` is sufficient for MVP because the project does not yet model `COMPLETED`. If a later milestone adds delivery/completion state, review eligibility can tighten to `COMPLETED` with an explicit migration and UI copy update.

## Persistence Flow

`SubmitReview(ctx, userID, input)`:

1. Validate input shape.
2. Generate `review_no`.
3. Call repository `SubmitReview(ctx, userID, reviewNo, input)`.
4. Repository opens one `trade_db` transaction.
5. Lock the owner-scoped order by `user_id + order_no`.
6. Reject non-`PAID` orders.
7. Lock the matching order item by `order_id + sku_id`.
8. Insert `reviews`.
9. Insert `outbox_events` row:
   - `aggregate_type`: `review`
   - `aggregate_id`: `review_no`
   - `event_type`: `review.submitted`
   - `topic`: `review.events`
   - `event_key`: product ID as a string
   - `payload`: JSON event envelope
10. Commit. If any insert fails, both review and Outbox rollback.

Outbox payload:

```json
{
  "event_id": "uuid",
  "event_type": "review.submitted",
  "review_no": "rev_001",
  "order_no": "ORD-1",
  "user_id": 7,
  "product_id": 1001,
  "sku_id": 2001,
  "rating": 5,
  "content": "手感很好，物流也快。",
  "occurred_at": "2026-08-24T12:00:00Z",
  "version": 1
}
```

For M5.2a the Outbox row may remain `PENDING`; publication and analytics consumption are M5.2b.

## API Contract

Extend `api/order/order.proto`:

```protobuf
rpc SubmitReview(SubmitReviewRequest) returns (ReviewResponse);

message SubmitReviewRequest {
  string order_no = 1;
  uint64 sku_id = 2;
  uint32 rating = 3;
  string content = 4;
}

message ReviewResponse {
  Review review = 1;
}

message Review {
  string review_no = 1;
  string order_no = 2;
  uint64 product_id = 3;
  uint64 sku_id = 4;
  uint32 rating = 5;
  string content = 6;
  string status = 7;
}
```

Gateway endpoint:

```text
POST /api/v1/orders/{order_no}/items/{sku_id}/reviews
```

Request:

```json
{
  "rating": 5,
  "content": "手感很好，物流也快。"
}
```

Response:

```json
{
  "review": {
    "review_no": "rev_001",
    "order_no": "ORD-1",
    "product_id": 1001,
    "sku_id": 2001,
    "rating": 5,
    "content": "手感很好，物流也快。",
    "status": "PUBLISHED"
  }
}
```

## Error Mapping

Domain to gRPC:

| Domain code | gRPC code |
| --- | --- |
| `INVALID_ARGUMENT` | `InvalidArgument` |
| `NOT_FOUND` | `NotFound` |
| `IDEMPOTENCY_CONFLICT` | `AlreadyExists` |
| `DEPENDENCY_TIMEOUT` | `DeadlineExceeded` |
| other | `Internal` |

Gateway maps existing order errors:

| gRPC code | HTTP status | JSON code | Message |
| --- | --- | --- | --- |
| `InvalidArgument` | 400 | `INVALID_ARGUMENT` | `invalid request` |
| `Unauthenticated` | 401 | `UNAUTHENTICATED` | `authentication required` |
| `NotFound` | 404 | `NOT_FOUND` | `resource not found` |
| `AlreadyExists` | 409 | `IDEMPOTENCY_CONFLICT` | `request conflict` |
| `DeadlineExceeded`, `Unavailable` | 504 | `DEPENDENCY_TIMEOUT` | `order service timeout` |
| other | 500 | `INTERNAL` | `internal server error` |

Raw SQL, Kafka, wallet, address, and dependency errors must not leak.

## Security and Privacy

- Gateway route is authenticated.
- Gateway forwards bearer and valid trace metadata through `orderclient`.
- `order-service` derives user ID from JWT metadata and checks order ownership.
- Review content is user-generated text. It is stored and emitted to `review.events`; M5.2a does not add moderation, so the UI must treat it as untrusted display text.
- The Outbox event excludes address, phone, wallet amounts, JWT, API keys, and raw order item JSON.

## Validation Strategy

Automated checks:

- Schema contract test asserts `reviews` table, uniqueness, rating check, FK to own trade tables, and `review.events` topic support via existing `outbox_events`.
- Domain service tests cover invalid rating/content, non-owner order, unpaid order, SKU not in order, duplicate review, and successful review.
- Repository tests cover one-transaction insert of review and Outbox, duplicate review mapping, and rollback when Outbox insert fails.
- gRPC server tests cover authenticated `SubmitReview` and error mapping.
- Gateway client/handler tests cover metadata propagation, route request mapping, invalid input, stable errors, and response shape.

Baseline validation:

```text
gofmt -w api/order services/order-service apps/gateway
go test ./services/order-service/... -count=1
go test ./apps/gateway/... -count=1
go test ./... -count=1
go vet ./...
git diff --check
```

## Milestone Boundary

M5.2a is complete when a user-scoped paid order item can be reviewed once, the review is persisted atomically with a `review.events` Outbox row, and Gateway exposes a stable authenticated HTTP endpoint. It does not prove Kafka publication or analytics consumption.
