# M5.2b Review Events Kafka Analytics Design

## Goal

M5.2b closes the backend event loop started in M5.2a: `review.events` rows written to `trade_db.outbox_events` are published to Kafka, consumed idempotently, and persisted into a minimal review analytics read model.

## Current Behavior

M5.2a added authenticated review submission:

- `POST /api/v1/orders/{order_no}/items/{sku_id}/reviews`.
- `trade_db.reviews`.
- `review.events` Outbox rows inserted in the same transaction as the review.

The existing `order-service/internal/outbox` worker publishes `inventory.reservation.confirm`, but it is hard-coded to that topic and payload shape. `review.events` rows currently remain `PENDING`.

The project already has Kafka topics for `review.events` and `behavior.events`. There is no analytics service, no review event consumer, and no read model for product rating statistics or event inspection.

## Scope

M5.2b includes:

- Generalize the order Outbox publisher so it can publish both:
  - `inventory.reservation.confirm`
  - `review.events`
- Preserve existing reservation confirmation behavior and tests.
- Add trade-owned review analytics tables:
  - `review_event_consumptions`
  - `review_event_records`
  - `product_review_stats`
- Add a `review.events` Kafka consumer runtime in `order-service`.
- Parse and validate the M5.2a review event payload.
- Persist consumer idempotency and stats updates in one `trade_db` transaction.
- Publish malformed review events to `review.events.deadletter` only after the DLQ producer acknowledges, then commit the original offset.
- Record M5.2b progress in `docs/TASKS.md`.

M5.2b excludes:

- `behavior.events`.
- Full operations UI or admin auth.
- Product-service aggregate rating updates.
- Review moderation, deletion, editing, or media.
- Cross-service database access.

## Why Keep Analytics in `order-service`

The project has fixed MVP service boundaries and no `analytics-service`. Adding a sixth service would expand runtime, deployment, config, ownership, and Gateway surface for a narrow milestone. For M5.2b, the review analytics read model stays inside `trade_db` and `order-service` because the source event is produced from trade-owned review data and the consumer does not need to call other services.

This is intentionally a minimal read model, not a full marketing or BI subsystem. If later milestones need broader behavior analytics, a dedicated analytics owner can be introduced with an explicit service-boundary design.

## Data Model

Add to `trade_db`:

```sql
CREATE TABLE review_event_consumptions (
    event_id CHAR(36) NOT NULL,
    consumer_group VARCHAR(128) NOT NULL,
    status VARCHAR(32) NOT NULL,
    consumed_at DATETIME(3) NULL,
    created_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
    updated_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),
    PRIMARY KEY (event_id, consumer_group)
) ENGINE=InnoDB;
```

```sql
CREATE TABLE review_event_records (
    id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    event_id CHAR(36) NOT NULL,
    review_no VARCHAR(64) NOT NULL,
    order_no VARCHAR(64) NOT NULL,
    user_id BIGINT UNSIGNED NOT NULL,
    product_id BIGINT UNSIGNED NOT NULL,
    sku_id BIGINT UNSIGNED NOT NULL,
    rating TINYINT UNSIGNED NOT NULL,
    content VARCHAR(1000) NOT NULL,
    occurred_at DATETIME(3) NOT NULL,
    created_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
    PRIMARY KEY (id),
    UNIQUE KEY uq_review_event_records_event (event_id),
    UNIQUE KEY uq_review_event_records_review (review_no),
    KEY idx_review_event_records_product_created (product_id, occurred_at)
) ENGINE=InnoDB;
```

```sql
CREATE TABLE product_review_stats (
    product_id BIGINT UNSIGNED NOT NULL,
    review_count BIGINT UNSIGNED NOT NULL DEFAULT 0,
    rating_sum BIGINT UNSIGNED NOT NULL DEFAULT 0,
    rating_avg DECIMAL(4,2) NOT NULL DEFAULT 0.00,
    last_review_at DATETIME(3) NULL,
    updated_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),
    PRIMARY KEY (product_id)
) ENGINE=InnoDB;
```

`product_review_stats` is a derived read model. `reviews` remains the source of submitted reviews, and `outbox_events` plus Kafka remain the source of replayable analytics events.

## Outbox Publication

Replace the hard-coded confirmation-only worker with a generic event publisher shape:

```go
type Event struct {
    ID         uint64
    EventID    string
    Topic      string
    Key        string
    Payload    []byte
    Status     Status
    Attempts   int
    LeaseUntil time.Time
    ClaimToken string
}
```

The repository leases rows from `outbox_events` where `topic IN (...)`. For M5.2b, the allowed topics are:

- `inventory.reservation.confirm`
- `review.events`

Publication uses the row's `topic`, `event_key`, and raw JSON `payload`. It does not re-marshal topic-specific payloads. This reduces duplication and ensures the exact event persisted by the business transaction is the event sent to Kafka.

Existing confirmation tests must still prove:

- failed publish returns event to `PENDING`;
- expired `PROCESSING` lease can be reclaimed;
- stale claim cannot mark or retry another worker's lease;
- publisher calls are bounded by timeout.

New review publication tests must prove:

- `review.events` rows are leased and published with `Topic=review.events`;
- Kafka key equals Outbox `event_key`;
- raw payload is not modified;
- unrelated topics are not leased.

## Review Event Consumer

Add `services/order-service/internal/analytics` with:

- `ReviewEvent` payload DTO.
- `ReviewConsumer` Kafka adapter.
- `ReviewEventHandler`.
- `MySQLRepository` for idempotency, event record, and stats update.

Consumer group:

```text
order-review-analytics-v1
```

Consumer flow:

1. Fetch one Kafka message from `review.events`.
2. Decode JSON payload.
3. If malformed, publish to `review.events.deadletter` with:
   - `reason`
   - `raw_event_base64`
4. Commit original offset only after DLQ publish succeeds.
5. For valid payload, call `ReviewEventHandler.HandleReviewEvent`.
6. Handler validates stable fields:
   - `event_id` non-empty UUID string
   - `event_type == "review.submitted"`
   - `review_no`, `order_no`, `user_id`, `product_id`, `sku_id` present
   - `rating` in `1..5`
   - `content` non-empty and <= 1000 runes
   - `occurred_at` parseable
   - `version == 1`
7. Repository transaction:
   - insert `(event_id, consumer_group, PROCESSING)`;
   - if already `SUCCEEDED`, treat as success and commit offset;
   - if already `PROCESSING`, return retryable error and do not commit offset;
   - insert `review_event_records`;
   - upsert `product_review_stats`;
   - mark consumption `SUCCEEDED`.
8. Commit Kafka offset after handler success.

Stats update:

```sql
INSERT INTO product_review_stats (product_id, review_count, rating_sum, rating_avg, last_review_at)
VALUES (?, 1, ?, ?, ?)
ON DUPLICATE KEY UPDATE
  review_count = review_count + 1,
  rating_sum = rating_sum + VALUES(rating_sum),
  rating_avg = ROUND(rating_sum / review_count, 2),
  last_review_at = GREATEST(COALESCE(last_review_at, VALUES(last_review_at)), VALUES(last_review_at));
```

The implementation must compute the updated average from the updated `rating_sum` and `review_count`, not from stale pre-update values. If MySQL expression order is ambiguous, use a transaction with `SELECT ... FOR UPDATE` and explicit update instead.

## Runtime Wiring

`order-service/cmd/main.go` will run:

- generic Outbox worker for confirmation and review topics;
- payment recovery worker;
- review analytics Kafka consumer.

The consumer uses `AI_SHOPPING_KAFKA_BROKERS` from existing runtime config. Add YAML config under order-service:

```yaml
ReviewAnalytics:
  Enabled: true
  CallTimeout: 1s
```

If disabled, the order service still starts and can submit reviews; `review.events` publication still works. Consumer disablement is for local development and targeted tests, not for production parity.

## Error Handling

Outbox publisher:

- Kafka publish failure: mark row `PENDING` with bounded `next_retry_at`.
- State transition failure: return stable worker error, leave row recoverable by lease expiry.
- Invalid outbox payload for confirmation no longer blocks generic publication because raw payload is forwarded. Confirmation validation remains in the product consumer.

Review consumer:

- Malformed JSON or invalid fixed fields: publish DLQ and commit.
- Handler dependency or database error: do not commit; Kafka redelivery retries.
- Duplicate already-succeeded event: commit without applying stats again.
- Duplicate currently-processing event: return error and do not commit.

No raw SQL, database DSN, Kafka broker body, JWT, address, phone, wallet data, or stack trace is returned to users.

## Security and Privacy

Review content is user-generated text. It is stored in `reviews`, published in `review.events`, and copied into `review_event_records`. Operators and future UI must treat it as untrusted display text.

The event payload excludes address, phone, wallet amounts, JWT, API keys, and raw order item JSON. The consumer must not enrich events by querying user-service or product-service for additional PII.

## Validation Strategy

Automated checks:

- Schema contract tests assert analytics tables and constraints in base schema and migration.
- Outbox tests cover generic topic leasing and publication for `review.events`, plus existing confirmation behavior.
- Analytics repository tests cover first event, duplicate `SUCCEEDED`, duplicate `PROCESSING`, stats increment, and rollback on stats failure.
- Analytics consumer tests cover valid message commit, malformed message DLQ then commit, handler failure without commit, and DLQ publish failure without commit.
- Runtime config tests cover enabled/disabled consumer wiring without connecting to Kafka.

Commands:

```text
gofmt -w services/order-service deploy/mysql docs
go test ./services/order-service/... -count=1
go test ./... -count=1
go vet ./...
git diff --check
```

No normal test may require a live Kafka broker. Any real Kafka smoke test must be explicitly gated.

## Milestone Boundary

M5.2b is complete when a submitted review can produce a `review.events` Outbox row, the generic Outbox worker can publish that row to Kafka, and the review analytics consumer can idempotently update the minimal read model from Kafka messages. It does not complete behavior events, operations UI, or product aggregate rating display.
