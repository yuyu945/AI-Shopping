# M5.2c Operations and Behavior Events Design

## Goal

M5.2c completes the remaining M5 backend and frontend closure: a minimal operations console can inspect knowledge document processing, Agent runs, and event health, while user behavior events are reliably written through Outbox, published to Kafka, consumed idempotently, and exposed through a read-only event overview.

## Current Behavior

M5.1c added the user web app. M5.2a/b added review submission, `review.events` Outbox publication, and review analytics consumption.

The remaining gaps are:

- `knowledge-service` supports upload and retrieval, but has no document list, document detail, failure reason, chunk/version detail, or operator retry API.
- `agent-service` stores `trace_id`, model name, prompt version, timestamps, and Step input/output JSON, but the public `GetRun` path is user-owned and does not expose ops list or redacted diagnostics.
- `order-service` analytics currently consumes only `review.events`; `behavior.events` is defined in architecture docs but is not produced, consumed, or queryable.
- `apps/web` has user pages only; it has no operations pages matching `docs/interaction.md` section 5.

## Scope

M5.2c includes:

- Add `knowledge-service` gRPC methods for document list, document detail, and failed-document retry.
- Add Gateway operations HTTP routes for knowledge documents, preserving existing upload behavior.
- Add `agent-service` gRPC methods for operations Run list and Run detail.
- Return redacted Agent Step input/output JSON in operations detail; never return raw tokens, secrets, phone numbers, addresses, JWTs, or model provider internals.
- Add Gateway operations HTTP routes for Agent Run list/detail.
- Add `behavior.events` Outbox production for selected user actions at Gateway boundary.
- Add `behavior.events` Kafka consumer in `order-service` analytics with idempotency and dead-letter behavior matching review analytics.
- Add minimal read-only analytics overview endpoints for review and behavior events.
- Add operations pages to `apps/web`:
  - knowledge documents list/upload/detail/retry;
  - Agent Run list/status filter/detail/timeline;
  - event overview.
- Update `docs/TASKS.md`, `docs/architecture.md`, and `docs/interaction.md` if implementation changes any contract wording.

M5.2c excludes:

- A separate `analytics-service`.
- A full role/RBAC system or marketing admin backend.
- Cross-service database reads.
- Editing or deleting knowledge documents.
- Manual replay from dead-letter queues.
- Real-time live Agent streaming beyond current replay/polling SSE behavior.
- Product aggregate rating display in product-service.

## Authorization Boundary

MVP operations routes will use a minimal explicit operator gate at Gateway:

- Existing user JWT remains required.
- Gateway treats a request as operations-authorized only when the authenticated token is present and `X-AI-Shopping-Operator: true` is supplied.
- This is a local MVP guard, not production RBAC. It keeps operations routes separate from user routes and prevents accidental anonymous access without adding a new auth subsystem.

All operations HTTP paths live under:

```text
/api/v1/ops/*
```

The frontend operations navigation is separate from the user shopping navigation. User pages never call ops endpoints.

## Knowledge Operations

Extend `api/knowledge/knowledge.proto`:

```text
ListDocuments(product_id, doc_type, status, page_size, page_token)
GetDocument(document_no)
RetryDocument(document_no)
```

Document DTO adds operational fields:

- `file_name`
- `content_type`
- `file_size_bytes`
- `chunk_count`
- `embedding_model`
- `is_current_ready`
- `error_code`
- `error_message`
- `created_at`
- `updated_at`
- `processed_at`
- `ready_at`

Document detail includes ordered chunks with:

- `chunk_id`
- `chunk_index`
- `section`
- `source_page`
- `content_hash`
- `status`
- `vector_ref`

Retry semantics:

- Only `FAILED` documents can be retried.
- Retry runs in one `knowledge_db` transaction:
  - update document `FAILED -> PENDING`;
  - clear `error_code`, `error_message`, `processed_at`;
  - insert a new `knowledge.document.ingest` Outbox event with a new `event_id`;
  - keep existing chunks for audit; ingest processing remains idempotent by chunk keys.
- Retry returns the document immediately and does not wait for parsing or embedding.
- Retrying `PENDING`, `PROCESSING`, or `READY` returns `INVALID_ARGUMENT`.

## Agent Operations

Extend `api/agent/agent.proto`:

```text
ListRuns(status, user_id, page_size, page_token)
GetRunOps(run_id)
```

Ops run summary includes:

- `run_id`
- `session_no`
- `user_id`
- `status`
- `trace_id`
- `model_name`
- `prompt_version`
- `step_count`
- `error_code`
- `error_message`
- `started_at`
- `ended_at`
- `created_at`

Ops run detail includes:

- the summary fields;
- `final_text`;
- verified recommendation snapshots;
- ordered Steps with `attempt`, timestamps, latency, error fields, and redacted input/output JSON.

Redaction rules:

- JSON object keys matching `authorization`, `token`, `jwt`, `password`, `secret`, `api_key`, `phone`, `mobile`, `address`, `raw_prompt`, `provider_response`, or `credentials` are replaced with `"[REDACTED]"`.
- Long string values are truncated to 500 runes.
- Invalid JSON is never returned raw; the response uses `{"redaction_error":"invalid_json"}`.
- Redaction occurs in `agent-service` before Gateway serialization.

The existing user-owned `GetRun` API keeps its current behavior and does not expose ops-only fields.

## Behavior Events

M5.2c records selected user behavior at Gateway boundary because Gateway already observes authenticated HTTP requests and can write behavior intent without coupling business services together.

Add a small Gateway-owned table in `trade_db` for reliable behavior Outbox:

```sql
CREATE TABLE behavior_outbox_events (
    id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    event_id CHAR(36) NOT NULL,
    user_id BIGINT UNSIGNED NOT NULL,
    event_type VARCHAR(64) NOT NULL,
    topic VARCHAR(128) NOT NULL,
    event_key VARCHAR(128) NOT NULL,
    payload JSON NOT NULL,
    status VARCHAR(32) NOT NULL DEFAULT 'PENDING',
    attempts INT NOT NULL DEFAULT 0,
    next_retry_at DATETIME(3) NULL,
    lease_until DATETIME(3) NULL,
    claim_token VARCHAR(64) NULL,
    last_error VARCHAR(255) NULL,
    created_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
    updated_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),
    PRIMARY KEY (id),
    UNIQUE KEY uq_behavior_outbox_event_id (event_id),
    KEY idx_behavior_outbox_status_retry (status, next_retry_at, id),
    KEY idx_behavior_outbox_user_created (user_id, created_at)
) ENGINE=InnoDB;
```

Initial behavior event types:

- `product.viewed` on product detail lookup.
- `cart.item_added` after cart item creation succeeds.
- `agent.run_started` after Agent run creation succeeds.
- `order.created` after order creation succeeds.
- `payment.submitted` after wallet payment request returns a stable backend result.

Behavior payload rules:

- Include `event_id`, `event_type`, `user_id`, `occurred_at`, `trace_id`, and `version`.
- Include only resource IDs, status, and safe enum/string snapshots needed for analysis.
- Do not include JWT, address snapshots, phone, review content, wallet balance, model prompts, or Tool payloads.
- Gateway failures to write behavior Outbox must not break the primary user operation; they are logged as operational errors with `trace_id`.

Add a Gateway behavior Outbox worker that publishes only `behavior.events` rows to Kafka with key `user_id`. This avoids extending `order-service` ownership to Gateway-specific outbox rows.

## Analytics Consumption and Overview

Extend `order-service/internal/analytics` to handle behavior analytics next to review analytics. For MVP, `order-service` remains the analytics owner to avoid adding a sixth service.

Add `trade_db` tables:

```sql
CREATE TABLE behavior_event_consumptions (
    event_id CHAR(36) NOT NULL,
    consumer_group VARCHAR(128) NOT NULL,
    status VARCHAR(32) NOT NULL,
    consumed_at DATETIME(3) NULL,
    created_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
    updated_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),
    PRIMARY KEY (event_id, consumer_group)
) ENGINE=InnoDB;
```

```sql
CREATE TABLE behavior_event_records (
    id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    event_id CHAR(36) NOT NULL,
    user_id BIGINT UNSIGNED NOT NULL,
    event_type VARCHAR(64) NOT NULL,
    trace_id VARCHAR(64) NOT NULL,
    resource_type VARCHAR(64) NOT NULL,
    resource_id VARCHAR(128) NOT NULL,
    payload JSON NOT NULL,
    occurred_at DATETIME(3) NOT NULL,
    created_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
    PRIMARY KEY (id),
    UNIQUE KEY uq_behavior_event_records_event (event_id),
    KEY idx_behavior_event_records_user_created (user_id, occurred_at),
    KEY idx_behavior_event_records_type_created (event_type, occurred_at)
) ENGINE=InnoDB;
```

```sql
CREATE TABLE analytics_dead_letters (
    id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    topic VARCHAR(128) NOT NULL,
    event_key VARCHAR(128) NOT NULL,
    reason VARCHAR(128) NOT NULL,
    raw_event_base64 MEDIUMTEXT NOT NULL,
    created_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
    PRIMARY KEY (id),
    KEY idx_analytics_dead_letters_topic_created (topic, created_at)
) ENGINE=InnoDB;
```

Behavior consumer group:

```text
order-behavior-analytics-v1
```

Consumer behavior:

- Valid behavior events insert consumption, event record, and mark `SUCCEEDED` in one transaction.
- Duplicate `SUCCEEDED` events are acknowledged without inserting duplicates.
- Duplicate `PROCESSING` events return retryable error and do not commit offset.
- Malformed or invalid behavior messages are published to `behavior.events.deadletter`, recorded in `analytics_dead_letters`, and then committed only after the DLQ publish succeeds.

Read-only overview API lives behind ops Gateway routes:

```text
GET /api/v1/ops/events/overview
```

It returns:

- recent review event records;
- product review stats;
- recent behavior event records;
- recent analytics dead letters;
- counts by event type and status.

The overview is diagnostic only. It does not mutate events or trigger replays.

## Operations Frontend

Add ops routes to `apps/web`:

- `#/ops/documents`
- `#/ops/agent-runs`
- `#/ops/events`

The layout follows `docs/interaction.md`:

- knowledge documents: list plus right-side detail panel on desktop, stacked detail on mobile; upload form at top; retry button only for `FAILED`;
- Agent runs: status filter and dense list on the left, Run detail and Step timeline on the right; selected Step shows redacted JSON;
- events: compact counters, recent review/behavior event tables, dead-letter table.

The frontend uses `X-AI-Shopping-Operator: true` only for ops client calls. It must not expose this header from user flows.

## Error Handling

Stable error mapping:

- `UNAUTHENTICATED`: no valid user token.
- `FORBIDDEN`: missing operator header or future operator authorization failure.
- `INVALID_ARGUMENT`: invalid filters, invalid retry state, invalid event payload.
- `NOT_FOUND`: missing document or run.
- `DEPENDENCY_TIMEOUT`: downstream gRPC/Kafka/DB timeout.
- `INTERNAL`: unexpected implementation failure with sanitized message.

Operations pages show short, actionable messages. They do not render raw database errors, Kafka broker messages, stack traces, raw provider responses, JWTs, addresses, phone numbers, or secrets.

## Security and Privacy

- Operator routes are separate under `/api/v1/ops`.
- User-owned APIs remain user-scoped and unchanged.
- Agent diagnostic data is redacted in `agent-service`, not only in the frontend.
- Behavior events intentionally store no PII-rich payloads.
- Review content remains in review analytics as already designed in M5.2b; overview displays it as untrusted plain text.

## Testing Strategy

Automated backend tests:

- Knowledge repository/service tests:
  - list filters by product, doc type, and status;
  - detail returns chunks and operational fields;
  - retry only accepts `FAILED`;
  - retry writes a new ingest Outbox event in the same transaction.
- Agent repository/service tests:
  - ops list filters by status and user;
  - ops detail returns trace/model/timestamps;
  - Step JSON redaction masks sensitive keys and truncates long strings;
  - invalid JSON is not returned raw.
- Gateway tests:
  - ops routes require auth and operator header;
  - ops routes map gRPC errors to stable HTTP codes;
  - behavior Outbox failures do not fail primary user requests.
- Behavior analytics tests:
  - valid event is consumed idempotently;
  - duplicate `SUCCEEDED` is skipped;
  - duplicate `PROCESSING` is retryable;
  - malformed event goes to DLQ and dead-letter record;
  - handler failure does not commit Kafka offset.
- Frontend tests:
  - knowledge ops list/detail/retry states;
  - Agent Run list/detail/timeline and redacted JSON rendering;
  - event overview counters and dead-letter rows;
  - ops client sends operator header only for ops calls.

Validation commands:

```text
gofmt -w api services apps/gateway docs
npm --prefix apps/web test -- --run
npm --prefix apps/web run build
go test ./apps/gateway/... -count=1
go test ./services/knowledge-service/... -count=1
go test ./services/agent-service/... -count=1
go test ./services/order-service/... -count=1
go test ./... -count=1
go vet ./...
git diff --check
```

No normal test may require live Kafka, Milvus, MinIO, MySQL, or DashScope unless explicitly gated by existing integration guard environment variables.

## Milestone Boundary

M5.2c is complete when a local browser can:

- upload/list/detail/retry knowledge documents through ops pages;
- inspect Agent Run lists and redacted Step timelines with `trace_id`;
- view recent review/behavior event records and dead-letter diagnostics;
- trigger user behavior events from normal user flows without breaking those flows.

The backend must prove Outbox, Kafka consumer idempotency, retry/dead-letter handling, and redaction through automated tests. The implementation stays inside existing Gateway, knowledge-service, agent-service, and order-service boundaries.
